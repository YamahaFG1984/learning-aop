CHAPTER 11

用切面强制执行规范

一句话概括本章：与其在代码评审里反复提醒"别这样写"，不如让编译器自动帮你把关——这就是策略强制执行（policy enforcement）。

本章你将学到

  • 用 declare error / declare warning 让编译器主动报错，而不是等代码评审发现问题
  • 用切面实现分层架构检查、封装性检查、工厂模式强制、"不返回 null 集合"等团队规范
  • AOP 规则强制 vs. Checkstyle/PMD/ArchUnit 这类静态分析工具，该怎么选

1. 为什么需要"会自己报错"的规则

团队里总有一些默认共识："UI 层不能直接连数据库""对象只能通过工厂创建""仓储方法别返回 null，返回空集合"。 这些规则通常写在 Wiki 或代码评审清单里——也就是说，全靠人记住、靠评审员发现。一旦有人忘了， 代码就悄悄"违规"了，往往要等到出 bug 才会被发现。

AspectJ 提供了一种更狠的做法：把这些规则写成切面里的 declare error， 编译器在编译时会像检查语法错误一样检查它们——不满足规则，代码直接编译不过。

💡 类比

普通的代码规范文档，像是贴在墙上的"安全须知"，靠自觉遵守； declare error 更像是电梯里的"超重蜂鸣器"——只要不符合规则，系统直接不让你通过，不用靠人盯着。

2. 编译期检查是怎么工作的

declare error 的语法很简单：给它一个切点表达式和一段错误信息。 只要有代码触发了这个切点，AspectJ 编译器就会在那一行标红报错，就像用错类型一样。

2.1 例子：分层架构检查

书中的例子来自仓库 ch11/workspace/Section11.1AOPBasedPolicyEnforcement： 应用分成 web（界面）→ service（业务）→ repository（数据访问）→ 数据库 四层，规则是"只能跨越相邻一层调用，不能跳层"。

图 11-2　web 层绕过 service/repository 直接访问数据库——LayeringViolation 切面会在编译期抓到它
ch11/workspace/.../ajia/architecture/SystemArchitecture.aj（描述分层结构，供其它切面复用）
public aspect SystemArchitecture {
    pointcut webLayerCall()
        : call(* ajia.web..*.*(..));
    pointcut inWebLayer()
        : within(ajia.web..*);

    pointcut serviceLayerCall()
        : call(* ajia.service..*.*(..));
    pointcut inServiceLayer()
        : within(ajia.service..*);

    pointcut repositoryLayerCall()
        : call(* ajia.repository..*.*(..));
    pointcut inRepositoryLayer()
        : within(ajia.repository..*);

    pointcut dataLayerCall()
        : JDBCPointcuts.jdbcCall() || JPAPointcuts.jpaCall();
}
ch11/workspace/.../ajia/architecture/LayeringViolation.aj（真正报错的规则）
public aspect LayeringViolation {
    declare error
      : SystemArchitecture.dataLayerCall()
        && !SystemArchitecture.inRepositoryLayer()
      : "Only the repository layer is allowed to access the data layer";

    declare error
      : SystemArchitecture.webLayerCall()
        && !SystemArchitecture.inWebLayer()
      : "Only the UI layer is allowed to access itself";
    // ... 中间两条类似规则，见随书源码
}

这里的关键技巧是把"什么是某一层"抽成一组可复用的切点（SystemArchitecture）， 真正报错的规则切面只负责组合这些切点。这样以后重构包名，只需要改一个地方。

2.2 更多例子：封装性 & 工厂模式

本章还展示了几个常见的"用 Java 访问修饰符做不到，但用 AspectJ 能做到"的规则：

规则怎么写
不要把字段设为 publicdeclare warning : get(public !final * *) || set(public !final * *) : "..."
只允许 OrderService 修改 Orderdeclare error : call(* Order.add*(..)) && !within(OrderService+) : "..."
只允许工厂类创建 Product在 ProductFactory 内嵌一个 static aspect，规则是 call(Product.new(..)) && !within(ProductFactory+)

最后一条特别有意思：它相当于给 Java 补上了 C++ 里的 "friend" 语义——只有指定的类能调用某个构造方法， 普通的 public/private 做不到这种"只对某个类开放"的精细控制。

⚠️ Spring AOP 做不到这些

因为这些例子都依赖 call() 切点或 declare error（编译期语法）， 而 Spring AOP 是运行时动态代理，既不能拦截 new 构造调用，也不产生编译错误。 这类"设计规则"类的强制，必须用真正的 AspectJ 织入（编译期或加载期）。

3. 编译期检查的局限 & 运行时检查补位

declare error 虽然强大，但只能用"静态可判定"的切点，因此做不到：

  • 依赖运行时信息的判断（比如 this()、if()、cflow() 不能用在 declare 里）
  • 检测"缺少什么"，比如空的 catch 块——切点只能匹配存在的连接点
  • 跨多个连接点的关联检查，比如"加的锁有没有对应释放"
  • 风格类问题，比如方法太长、没写注释

这些场景需要运行时通知（比如 after() returning）来补位。 书中给出一个例子：仓储方法不应该返回 null 集合，而应该返回空集合——这是运行时才能检测到的："方法真的返回了 null"这件事必须等它执行完才知道。

现代写法：用 @AspectJ 注解检测 Repository 返回 null 集合
@Aspect
public class RepositoryNullReturnDetector {
    private static final Logger log =
        LoggerFactory.getLogger(RepositoryNullReturnDetector.class); // SLF4J，取代书中的 Log4j 1.x

    @AfterReturning(
        pointcut = "execution((java.util.Map+ || java.util.Collection+) *..*Repository.*(..))",
        returning = "result")
    public void checkNullReturn(Object result) {
        if (result == null) {
            log.error("Repository 方法返回了 null 集合，应返回空集合", new Throwable());
        }
    }
}

4. 和静态分析工具（Checkstyle / PMD / ArchUnit）比，该用哪个？

代码分析工具
  • 能跨方法/跨类分析（比如判断锁有没有配对释放）
  • 能检查源码层面的东西：命名规范、注释缺失、代码风格
  • 大多在编译期或 IDE 里就能跑，反馈快
  • 没有运行时上下文——检测不了"当前调用线程是谁"这类信息
AspectJ 规则强制
  • 能表达连接点级别的精确规则（谁在调用谁、在哪个控制流里）
  • 能在运行时用真实上下文做判断（当前线程、当前登录用户……）
  • 写法通常只需要几行切点，很适合项目专属规则
  • 做不到"缺失检测"和风格类检查
🔧 现代补充：ArchUnit

本章写作时（2010 年前后），Checkstyle/PMD/FindBugs 是主流的静态分析工具。今天做"架构分层检查"， 很多团队会优先选择 ArchUnit——它是一个基于 JUnit 5 的库，用普通 Java 代码写规则 （比如 classes().that().resideInAPackage("..service..").should().onlyBeAccessed().byAnyPackage("..web..")）， 跑在 CI 的单元测试阶段，不需要在主构建里引入 AspectJ 织入器，学习成本更低。

但 ArchUnit 是"事后扫描字节码"，没法像 declare error 那样在编译的一瞬间把光标定位到违规那一行， 也无法结合运行时上下文（比如 cflow）做判断。两者并不互斥：架构分层这种"结构性"规则， ArchUnit 通常够用又轻量；需要连接点精度或运行时判断的规则（工厂强制、字段访问限制、线程安全策略）， AspectJ 仍然是更合适的工具。

小结 & 自测

  • declare error 和普通的运行时异常检查有什么本质区别？
    declare error 是编译期机制：只要代码里存在匹配的连接点，编译器就直接报错，代码根本编译不过，不需要真正跑起来触发那条路径；运行时检查则必须等代码执行到那一行才能发现问题。
  • 为什么 declare error 不能用 this()、if()、cflow() 这类切点？
    因为编译期还没有"运行中的对象/调用栈"，只能用能在源码静态分析阶段就确定下来的切点（比如 call、within、get/set），这类切点叫"静态可判定切点"。
  • 为什么 Spring AOP 无法实现"只有工厂类能创建 Product"这条规则？
    因为这条规则需要拦截构造方法调用（call(Product.new(..))），而 Spring AOP 基于运行时动态代理，只能围绕已经存在的 Bean 方法调用做增强，不能拦截 new 关键字。
  • 今天做架构分层检查，ArchUnit 和 AspectJ 的 declare error 该怎么选？
    纯粹的包依赖方向检查，ArchUnit 更轻量、不需要引入织入器，跑在单元测试里就行；如果需要连接点级别的精确匹配或运行时上下文（比如结合当前线程、调用链判断），仍然需要 AspectJ。
  • 为什么"不返回 null 集合"这条规则要在运行时而不是编译期检查？
    因为"方法实际返回了什么值"是运行时才知道的信息，编译期只能看到方法签名和代码结构，看不出某次具体调用的返回值是不是 null。
