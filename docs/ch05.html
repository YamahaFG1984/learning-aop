第 5 章

用静态切面修改结构

一句话概括本章：前几章用切面“插入行为”，这一章教你用切面“改造结构”——给已有的类偷偷加字段、加方法，甚至让它多实现一个接口。

本章你将学到

  • 类型间声明（Inter-type Declaration，ITD）：从切面里给别的类加字段/方法/构造器
  • 用 declare parents 给已有类“贴上”新接口或新父类，实现 Java 没有的“混入（mixin）”
  • 用 declare error / declare warning 在编译期就拦住违规代码
  • 用 declare soft 把烦人的受检异常变成非受检异常

1. 为什么需要“静态”切面

第 4 章的通知（advice）改的是行为：在方法执行前后插一段代码。但有些问题光靠“插代码”解决不了—— 比如你想让若干个毫不相关的类都拥有“属性变更通知”能力，或者想给第三方库里的一个类加一个字段，而你根本改不了它的源码。 这类需求改的是类的结构（有哪些字段、实现了哪些接口），AspectJ 把这种切面叫做静态切分（static crosscutting）， 核心工具就是类型间声明（ITD）。

💡 类比

普通的 Java 继承像是“出生时就定好血统”：一个类的父类和接口在写代码那一刻就固定了。 ITD 更像是“成年后办理的资质认证”——切面在编译期悄悄给某个类补办一张“新技能证书”（新字段/新方法/新接口）， 业务类自己完全不知道这件事发生过。

2. 类型间声明（ITD）：给别的类加东西

ITD 的语法很好认：正常写字段/方法时，把类名塞进方法名（或字段名）前面，就表示“这个成员属于那个类，不属于我自己”。 书中经典例子是给 Java Bean 补上“属性变更通知”功能——用一个空接口 BeanSupport 做标记， 真正的实现全部由切面通过 ITD 注入：

ch05/workspace/Section5.1.3MixingWithMixins — BeanSupport.java（标记接口，本身空空如也）
package ajia.bean;

public interface BeanSupport {
}
ch05/workspace/Section5.1.3MixingWithMixins — BeanMakerAspect.aj（真正干活的切面）
public aspect BeanMakerAspect {
    // 给所有 BeanSupport 实现类"塞"一个新字段
    private PropertyChangeSupport BeanSupport.propertyChangeSupport;

    // 给所有 BeanSupport 实现类"塞"两个新方法
    public void BeanSupport.addPropertyChangeListener(PropertyChangeListener l) {
        propertyChangeSupport.addPropertyChangeListener(l);
    }
    public void BeanSupport.removePropertyChangeListener(PropertyChangeListener l) {
        propertyChangeSupport.removePropertyChangeListener(l);
    }

    pointcut beanCreation(BeanSupport bean)
        : initialization(BeanSupport+.new(..)) && this(bean);

    after(BeanSupport bean) returning : beanCreation(bean) {
        bean.propertyChangeSupport = new PropertyChangeSupport(bean);
    }
    // around 通知拦截所有 setter，比较新旧值后触发通知（略，见仓库源码）
}

效果：Customer 类只写了 implements BeanSupport 这一行， 编译后却"自带" addPropertyChangeListener、自动在每个 setter 后发出属性变更事件—— 这些代码 Customer.java 里一行都没写，全部来自切面。

3. declare parents：给类“贴”新接口/新父类（mixin）

ITD 常和 declare parents 搭配使用：先用它让一批类"承认"自己实现了某个接口， 再用 ITD 给这个接口补上默认实现——这就是 AspectJ 版的 mixin（混入）， 相当于给 Java 补上了它一直没有的"多重实现继承"。

语法（并非某个具体示例文件，用来说明用法）
declare parents: banking.entities.* implements BeanSupport;
// 也可以按注解匹配，比如让所有 @Entity 类自动获得 BeanSupport 能力
declare parents: @Entity * implements BeanSupport;
⚠️ 现代 Java 上的注意事项

AspectJ 1.9.x 在 Java 17/21 上依旧完整支持 ITD 与 declare parents，语法几乎和书里一模一样。 但要注意两点：① Java 8 之后接口本身也能写 default 方法，很多当年只能靠 mixin 实现的“默认实现”需求， 现在用接口默认方法就能直接解决，不必上 AspectJ；② 如果目标类位于 JDK 内部模块（java.*）， 模块系统（JPMS）会限制反射与织入访问，实践中请只对你自己的业务类做 ITD。

4. declare @type：给类型贴注解

和 ITD 类似，你也可以让切面在编译期给某个类型“贴上”一个注解，常用来给一批符合某种特征的类统一打标签， 以便其他切点用 @within、@target 之类的注解匹配去命中它们。

语法示例
declare @type: @PrivacyControlled * : @Tracked;
// 意思：所有标了 @PrivacyControlled 的类，编译期自动再打上 @Tracked

5. declare error / declare warning：把规范检查提前到编译期

这是本章里“性价比”很高的一招：用切点描述一种你不想看到的写法，一旦有代码命中，编译直接报错或警告， 而不是等到 code review 或线上事故才发现。第 11 章会把这个技巧发扬光大，用来做团队级的架构规范检查。

语法示例
declare error : call(* Runtime.exec(..)) : "禁止直接调用 Runtime.exec，请走审计过的 ProcessRunner";
declare warning : call(* java.io.*.*(..)) && within(com.acme.service..*) : "service 层不要直接做文件 IO";

6. declare soft：把受检异常“软化”成非受检异常

Java 的受检异常（checked exception）经常逼着你在完全无法处理异常的地方写一堆 try/catch 或 throws 样板代码。declare soft 可以指定：在某个切点范围内， 某种受检异常自动被包装成 AspectJ 提供的 org.aspectj.lang.SoftException（一个运行时异常）， 调用方就不必强制处理它了。

ch05/workspace/Section5.6SofteningCheckedException
public aspect SofteningTestAspect {
    declare soft : RemoteException : call(void TestSoftening.perform());
}

// TestSoftening.perform() 原本声明 throws RemoteException，
// 但在这个切点范围内调用它时，异常被自动“软化”，调用处不必写 try/catch
🔧 现代写法提示

ITD、declare parents、declare error/warning/soft 都是 AspectJ 原生语法（native syntax，.aj 文件）独有的能力——纯注解风格的 @AspectJ 语法（第 7 章会讲） 不支持静态切分。所以如果你的项目主要用注解写切面，但又想用本章这些能力，需要保留 .aj 文件， 并在 pom.xml 里用现代维护版的编译插件 dev.aspectj:aspectj-maven-plugin （取代已停止维护的 org.codehaus.mojo:aspectj-maven-plugin）来编译，具体配置见附录 B/C 笔记。

小结 & 自测

  • ITD 和普通通知（advice）的本质区别是什么？
    通知修改的是“行为”（在某个连接点前后插入代码），而 ITD 修改的是“结构”——给已有类型静态地添加字段、方法、构造器，编译后这些成员就像原本就写在那个类里一样。
  • declare parents 能让一个类同时“继承”两个类的实现吗？
    不能直接继承两个类（Java 单继承限制仍在），但可以让类实现多个接口，再分别用不同切面通过 ITD 给每个接口提供实现，从而达到“多重实现继承”的效果，这就是 mixin。
  • declare error 和普通的单元测试相比，优势是什么？
    declare error 在编译期就拦截违规代码，写代码的人几乎无法忽略；而单元测试要跑起来才发现问题，且需要专门为规范检查写测试用例，覆盖不全时规范就形同虚设。
  • declare soft 软化之后的异常还需要 catch 吗？
    不强制。软化后的异常是运行时异常（SoftException），Java 编译器不会强制你处理它；如果你确实想处理，仍然可以 catch org.aspectj.lang.SoftException 并调用 getWrappedThrowable() 拿到原始异常。
