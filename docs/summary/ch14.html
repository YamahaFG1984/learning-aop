1. 事务管理为什么是横切关注点

电商下单场景：往购物车加一件商品，同时要从库存里扣掉一件。如果“扣库存”成功但“加购物车”失败， 系统就进入了不一致状态。解决办法是把两步操作包在一个事务里：要么都成功，要么都回滚，就像什么都没发生过。

传统写法要求每一个需要事务的方法，都手写“开始事务 → try 业务逻辑 → 成功就提交，异常就判断是否该回滚”这一整套模板代码。 这套模板和具体业务毫无关系，却要在几十上百个方法里重复——典型的横切关注点。

传统写法（每个事务方法都要重复）
public void businessMethod() {
    TransactionStatus ts = transactionManager.getTransaction(ta);
    try {
        // ... 真正的业务逻辑，占比可能只有 10% ...
        transactionManager.commit(ts);
    } catch (Throwable ex) {
        if (ta.rollbackOn(ex)) transactionManager.rollback(ts);
        else transactionManager.commit(ts);
        throw ex;
    }
}

2. 从零实现一个事务切面

仓库对应目录：ch14/workspace/Section14.5.2AnnotationDrivenTransactionManagement。 核心是一个 around 通知——注意它和上面传统写法的模板几乎一模一样， 只是把“业务逻辑”换成了 pjp.proceed()：

图 14-1　around 通知天然适合“包一层开始/结束逻辑”——事务、日志、缓存都是这个套路
AbstractTransactionManagementAspect.java（简化）
@Aspect
public abstract class AbstractTransactionManagementAspect {

    @Pointcut
    protected abstract void transactionalOp();

    @Around("transactionalOp()")
    public Object transact(ProceedingJoinPoint pjp) throws Throwable {
        var status = transactionManager.getTransaction(getTxAttribute(pjp));
        try {
            Object ret = pjp.proceed();
            transactionManager.commit(status);
            return ret;
        } catch (Throwable ex) {
            if (shouldRollback(ex)) transactionManager.rollback(status);
            else transactionManager.commit(status);
            throw ex;
        }
    }
}

子切面 AnnotationDrivenTransactionManagementAspect 只需要提供切点 （“匹配所有标了 @Transactional 的方法”）和“如何从注解里读出事务属性”这两块， 可以说：Spring 的 @Transactional 底层，本质上就是这样一个切面。

3. Spring 的三种事务配置方式

方式怎么配置本质今天还用吗
XML 驱动<tx:advice> + <aop:advisor>Spring AOP 代理不推荐，纯历史遗留
注解驱动@Transactional + @EnableTransactionManagementSpring AOP 代理（默认）✅ 现代标准做法
AspectJ 织入驱动@EnableTransactionManagement(mode = AdviceMode.ASPECTJ)编译期/加载期字节码织入，无代理仅在需要突破代理限制时使用
书中写法（XML 时代）
<tx:advice id="txAdvice">
  <tx:attributes>
    <tx:method name="find*" read-only="true"/>
  </tx:attributes>
</tx:advice>
推荐的现代写法（Spring Boot 3.x）
@Service
public class OrderService {

  @Transactional(readOnly = true)
  public Order find(Long id) { ... }

  @Transactional
  public void addProduct(...) { ... }
}
🔧 现代化提示

引入 spring-boot-starter-data-jpa（或 starter-jdbc）后， Spring Boot 会自动装配一个 PlatformTransactionManager，你甚至不需要手写 JpaTransactionManager 这个 bean。@EnableTransactionManagement 在 Boot 里也常常隐式开启，很多项目直接标 @Transactional 就能用。

4. 自调用陷阱：和第 9 章的代理问题是同一个坑

默认的注解驱动事务是靠 Spring AOP 代理实现的（回忆第 9 章）：只有外部通过代理调用的方法才会被增强。 如果 OrderServiceImpl.placeOrder() 内部直接调用 this.chargeCard()， 这次调用完全绕开了代理，chargeCard() 上的 @Transactional 会被静默忽略—— 没有任何报错，只是事务没开启，是最容易踩、最难排查的坑之一。

图 14-2　代理模式在“方法边界”生效，AspectJ 织入直接改写字节码本身
⚠️ 什么时候才需要切到 AspectJ 织入模式

绝大多数项目用默认的注解驱动代理模式就够了。只有当你确实需要“自调用也生效”， 或者要给非 Spring 管理的普通对象（比如领域实体，见第 16 章）加事务时， 才值得引入编译期/加载期织入的额外复杂度。别为了“可能用到”而提前上织入。

5. 顺带实现：事务操作的自动重试（容错）

事务操作有个好性质：失败就回滚，不留下任何痕迹，天然是幂等的，所以可以安全重试。 书中复用第 4 章的容错切面思路，写了一个 RetryFaultToleranceAspect， 用 around 通知包住可重试的操作，失败后按策略自动重试几次再放弃。

🔧 现代化提示

书中依赖已经停止维护的 Spring Batch 的 RetryTemplate（后来独立成了 Spring Retry 项目）。现代写法有两个选择：继续用 spring-retry（@Retryable 注解，本身也是靠 AOP 代理实现的）， 或者用更通用的 Resilience4j（@Retry）。两者思路和本章的自制切面完全一致——都是 “around 通知包住调用，失败后重新 proceed()”。

小结 & 自测

  • 为什么说事务管理是“教科书级”的横切关注点案例？
    因为“开始/提交/回滚”这套逻辑和具体业务无关，却几乎出现在每一个需要持久化操作的方法里，是横切关注点的典型特征。
  • Spring 默认的 @Transactional 是靠什么机制实现的？
    默认是 Spring AOP 的 JDK 动态代理/CGLIB 代理，只在通过代理对象调用方法时生效。
  • 为什么方法内部的自调用会让 @Transactional 失效？
    因为 this.method() 是直接在目标对象内部调用，完全没有经过外层的代理对象，代理里的事务通知自然不会被触发。
  • 什么情况下值得切换到 AspectJ 织入模式管理事务？
    需要自调用也能触发事务，或者要给非 Spring 管理的对象（如领域实体）加事务边界时；否则默认的代理模式更简单、足够用。
