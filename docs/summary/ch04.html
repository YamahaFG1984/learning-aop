CHAPTER 04

用动态切面修改行为

一句话概括本章：连接点是“在哪插手”，通知（advice）就是“插手时具体做什么”——本章讲清 5 种通知的区别，以及万能的 around 通知怎么写。

本章你将学到

  • before / after / after-returning / after-throwing / around 五种通知的语义与写法
  • 为什么只有 around 通知有 proceed()，它到底代表什么
  • 如何在通知里拿到方法参数、目标对象、返回值、异常等"连接点上下文"
  • 用真实例子搭一个缓存切面和一个失败重试切面

1. 通知：连接点上要执行的动作

如果说切点（pointcut）回答的是"在哪个时刻插手"，那通知（advice）回答的就是"插手时具体干什么"。 AspectJ 提供 5 种通知，覆盖了几乎所有横切场景：

图 4-1　五种通知相对于"被通知方法"的时机关系
通知类型执行时机典型用途
before方法执行前权限校验、参数校验、记录开始时间
after returning方法正常返回后记录成功日志、处理返回值
after throwing方法抛出异常后异常日志、告警
after（finally）不论成功失败都执行释放资源、结束计时
around包裹整个方法执行缓存、重试、事务、性能统计——凡是需要"改变是否执行/执行几次/改返回值"的场景
💡 类比

把方法调用想象成一次“送快递”。before 是快递员出发前的安检；after returning 是签收成功后的短信通知； after throwing 是包裹丢失后的理赔提醒；after 是不管有没有签收都会发的“已完结”记录； 而 around 相当于你自己就是那个快递公司——可以决定要不要真的发货、发几次、甚至直接拿仓库里现成的货顶替（这就是缓存的原理）。

2. around 通知与 proceed()：唯一能"改变是否执行"的通知

只有 around 通知里能调用 proceed()——它的意思是"现在，请真正执行一次被织入的原始逻辑"。 不调用 proceed()，原方法体就完全不会执行；调用它一次，等价于正常执行一次；甚至可以调用多次（比如重试）、或者带着不同参数调用（比如篡改输入）。

图 4-2　多个 around 通知叠加时形成"洋葱"结构：每一层的 proceed() 都是调用更内一层
around 通知的基本形状（传统语法）
Object around(Connection connection)
    : connectionOperation(connection) {
    long startTime = System.nanoTime();
    Object ret = proceed(connection);      // 真正执行原方法
    System.out.println("耗时: " + (System.nanoTime() - startTime));
    return ret;                            // around 必须显式返回值
}

3. 实战一：用 around 通知实现缓存

仓库 ch04/workspace/Section4.4.2ImplementingSimpleCaching 里有一个很经典的缓存切面例子：先定义一个 @Cachable 注解标记"这个方法的返回值可以缓存"， 再写一个 around 通知——命中缓存就直接返回缓存值，不命中就调用 proceed() 执行原方法并把结果存起来。

ajia/caching/CacheAspect.aj（书中原版，基于已停止维护的 OSCache）
public aspect CacheAspect {
    private Cache cache = new Cache(true, true, false);

    public pointcut cachedAccess(Object arg, Cachable cachable)
        : execution(@Cachable * *(*)) && args(arg) && @annotation(cachable);

    Object around(Object arg, Cachable cachable) : cachedAccess(arg, cachable) {
        String key = cachable.cacheStore() + ":" + arg;
        try {
            return cache.getFromCache(key);
        } catch (NeedsRefreshException ex) {
            Object value = proceed(arg, cachable);
            cache.putInCache(key, value);
            return value;
        }
    }
}
书中依赖（已过时）
  • com.opensymphony.oscache —— 早已停止维护
  • 需要理解 NeedsRefreshException 这种反直觉的"用异常表示未命中"设计
推荐的现代写法
  • 用 ConcurrentHashMap 或 Caffeine 自己实现缓存存取，逻辑更直白
  • @AspectJ 注解语法，javac 直接可编译
现代等价写法：@AspectJ 语法 + 普通 Map 缓存
@Aspect
public class CacheAspect {
    private final Map<String, Object> cache = new ConcurrentHashMap<>();

    @Around("execution(@ajia.caching.Cachable * *(*)) " +
            "&& args(arg) && @annotation(cachable)")
    public Object cache(ProceedingJoinPoint pjp, Object arg, Cachable cachable) throws Throwable {
        String key = cachable.cacheStore() + ":" + arg;
        return cache.computeIfAbsent(key, k -> {
            try { return pjp.proceed(); }
            catch (Throwable t) { throw new RuntimeException(t); }
        });
    }
}
🚀 现实项目里怎么做

如果你的项目本来就用 Spring，完全不需要自己写这个切面——加上 spring-boot-starter-cache 依赖， 在方法上标一个 @Cacheable("chart") 注解就够了，Spring 会用它自己的 AOP 代理帮你实现同样的效果。 本节手写的版本，价值在于让你理解 @Cacheable 背后到底发生了什么——这正是学 AspectJ 的意义：先懂原理，再放心用框架。

4. 实战二：用 around 通知实现失败重试

ch04/workspace/Section4.3.3ImplementingFaultTolerance 展示了另一个经典场景：远程调用可能失败，用 @Idempotent（幂等，意味着"重试是安全的"）标记方法，切面负责自动重试。

ajia/faulttolerance/FailureHandlingAspect.aj（书中原版）
public aspect FailureHandlingAspect {
    private final int MAX_RETRIES = 3;

    Object around() : call(@Idempotent * *(..)) {
        int retry = 0;
        while (true) {
            try {
                return proceed();
            } catch (RemoteAccessException ex) {
                if (++retry > MAX_RETRIES) throw ex;
            }
        }
    }
}

这里用的是 call() 而不是 execution()——因为重试逻辑只需要在调用远程服务的那一侧生效，不需要侵入远程服务内部的实现（呼应第 3 章讲的 call vs. execution 的取舍）。

🚀 现实项目里怎么做

现代 Spring 项目通常直接用 Spring Retry（@Retryable 注解）或 resilience4j 来做重试和熔断， 它们本质上也是靠 AOP 代理 + around 逻辑实现的——理解了这一节，你就理解了 @Retryable 的工作原理。

5. 收集连接点上下文

通知光知道"什么时候执行"还不够，往往还需要知道"当时的参数是什么、目标对象是谁、抛出了什么异常"。这些信息统称为连接点上下文，主要通过在切点里声明参数来收集：

  • args(arg) — 收集方法参数
  • target(obj) — 收集方法调用的目标对象
  • @annotation(ann) — 收集方法上的注解实例
  • thisJoinPoint — 一个特殊变量，随时可用，包含连接点的文字描述、参数数组等反射信息（第 3 章追踪例子里已经见过）
✏️ 动手练习

打开 ch04/workspace/Section4.3.3ImplementingFaultTolerance，把 MAX_RETRIES 改成 1，多运行几次 RemoteClient （RemoteService.getReply() 有 75% 概率模拟失败），观察重试次数用尽后抛出异常的输出； 再试着把 around 换成 before 写同样的重试逻辑，你会发现根本写不出来——这就是"只有 around 能控制是否执行/执行几次"的直接证明。

小结 & 自测

  • 为什么只有 around 通知能实现缓存？
    因为缓存命中时需要"完全跳过原方法、直接返回缓存值"——这要求通知能决定是否执行原逻辑，而 before/after 系列通知无法阻止原方法执行，只有 around 的 proceed() 机制能做到。
  • after 和 after returning 的区别？
    after（finally）不管方法是正常返回还是抛异常都会执行；after returning 只在方法正常返回时执行，如果抛异常则不会触发。
  • around 通知里，忘记调用 proceed() 会发生什么？
    被通知的原方法体完全不会执行——这有时是有意为之（比如权限拦截直接拒绝），但更多时候是新手忘写导致的 bug。
  • 多个 around 通知同时作用在同一个方法上时，它们是什么关系？
    像洋葱一样层层嵌套：外层的 proceed() 调用的正是内层通知，最终才会到达原始方法体；调用顺序由切面优先级决定（第 6 章会讲）。
  • args()、target()、@annotation() 这些切点是用来做什么的？
    收集连接点上下文——把方法参数、目标对象、注解实例这些运行时信息，通过命名一致的参数传递给通知方法使用。
