第 7 章

深入 @AspectJ 注解语法

一句话概括本章：前几章你看到的都是 aspect / pointcut 这种“专属关键字”写法（传统语法），本章教你用纯 Java 注解（@Aspect、@Before…）写出一模一样的效果——这也是现在 Spring 项目里 99% 的人在用的写法。

本章你将学到

  • @AspectJ 注解语法与传统语法的对应关系（一张表全搞定）
  • 用方法参数绑定连接点上下文：JoinPoint、ProceedingJoinPoint、args()/target()
  • @AspectJ 语法做不到的事情：类型间声明、异常软化、特权切面
  • 什么时候该用 @AspectJ，什么时候必须回去用传统语法

1. 为什么会有第二套语法？

传统语法（aspect、pointcut、before() 这些关键字）需要专门的 ajc 编译器才能理解， 普通的 javac 和大多数 IDE 完全看不懂。这就像你写了一份合同，用的是只有律师事务所内部人员才认识的黑话——法律上没问题，但换个部门看就抓瞎。

@AspectJ 语法的思路很简单：找一个语义相近的 Java 元素，贴上一个注解，让它“客串”AOP 概念。 因为切面很像一个类，所以一个被 @Aspect 标注的类就是切面； 因为切点可以有参数，所以一个被 @Pointcut 标注的方法就是切点。 这样写出来的代码，任何 Java 编译器、任何 IDE、任何静态检查工具都能正常处理——它们只是不理解注解背后的“魔法”而已，但不会报错。

映射关系速查表

💡 类比

@AspectJ 语法就像“伪装成普通信件的合同”——内容和正式合同（传统语法）法律效力相同， 但因为格式看起来像普通信件，任何邮局（Java 工具链）都愿意处理它，不会因为“格式陌生”而拒收。

2. 命名切点 vs. 匿名切点

仓库里 ch07/workspace/Section7.4.1AdvisingWithAnonymousPointcut 展示了最简单的写法：直接把切点表达式塞进 @Before 注解，不单独命名。这适合非常简单、只用一次的场景：

ajia/monitoring/SystemHealthMonitor.java（匿名切点）
@Aspect
public class SystemHealthMonitor {
    HeartBeatListener heartBeatListener = new HeartBeatListener();

    @Before("execution(* *(..)) && !within(ajia.monitoring.*)")
    public void beatHeart() {
        heartBeatListener.beat();
    }
}

仓库里 Section7.4.1UtilizingReflectiveJoinPointContext 则把切点单独命名（traced()）， 这样它可以被多个通知复用，也更容易读：

ajia/tracing/Tracing.java（命名切点 + 反射式上下文）
@Aspect
public class Tracing {
    @Pointcut("execution(* *.*(..))")
    public void traced() {}

    @Before("traced()")
    public void trace(JoinPoint jp) {
        System.out.println("Entering " + jp);
    }
}

这里 JoinPoint jp 就是“反射式”获取上下文——不管当前拦到的是哪个方法，AspectJ 都会在运行时把一个描述 “这是谁、参数是什么”的对象塞给你，有点像 Java 反射里的 Method 对象，但专门为切面场景设计。

3. 更精确的上下文绑定：把参数“穿”进通知里

反射式访问简单但不够快、也没有编译期类型检查。更好的做法是用 args()、target()、this() 把连接点里的具体对象，直接绑定成通知方法的参数——类型明确，IDE 还能自动补全。

ajia/monitoring/ConnectionMonitor.java（命名切点 + 类型化上下文）
@Aspect
public class ConnectionMonitor {

    @Pointcut("call(* java.sql.Connection.*(..)) && target(connection)")
    public void connectionOperation(Connection connection) {}

    @Before("connectionOperation(connection)")
    public void monitorUse(Connection connection) {
        System.out.println("About to use " + connection);
    }
}
⚠️ 老 Java 版本的坑

书中提醒：用 javac 编译 @AspectJ 切面时，必须加 -parameters（书里写的是老版本的 -g:vars） 或在注解里写 argNames，否则编译器不会保留参数名，织入器就没法把切点里的 connection 和方法参数名对上号。现代 Maven/Gradle 编译插件建议直接开启 -parameters 编译选项，一劳永逸。

4. Around 通知与 ProceedingJoinPoint

传统语法里 proceed() 是关键字；@AspectJ 里没有关键字，改用一个特殊类型的参数 ProceedingJoinPoint（继承自 JoinPoint），调它的 proceed() 方法。 仓库里 ch07/workspace/Section7.4.3ProceedingWithOriginalJoinPointExecution 就是经典的性能计时切面：

ajia/monitoring/Monitoring.java（计时 around 通知）
@Aspect
public abstract class Monitoring {

    @Pointcut
    public abstract void monitored();

    @Around("monitored()")
    public Object measureTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        Object ret = pjp.proceed();               // 相当于传统语法里的 proceed()
        long end = System.nanoTime();
        System.out.println(pjp.getSignature().toShortString()
                + " took " + (end - start) + "ns");
        return ret;
    }
}

注意这里 monitored() 是一个抽象切点——这个类本身没定义“监控谁”， 留给子类去实现（比如“只监控 JDBC 调用”）。这是切面版的模板方法模式，第 6、12 章会再深入讲。

5. @AspectJ 语法做不到的三件事

因为整套设计必须兼容普通 javac，有些强行改变“类的结构 / 编译期规则”的功能没法实现：

  • 类型间声明（ITD）——不能用 @AspectJ 给已有类新增字段/方法（下一章 ch05 讲的功能）。普通 Java 编译器根本不知道“这个字段是切面偷偷加的”，所以干脆不支持；退而求其次可以用 @DeclareMixin 实现“混入接口”的效果。
  • 异常软化（declare soft）——把受检异常在编译期变成非受检异常，这依赖专用编译器修改编译期检查规则，javac 做不到。运行时部分（抛出 SoftException）可以用 @AfterThrowing 模拟，但调用方仍然被强制 catch，价值大打折扣。
  • 特权切面（privileged aspect）——绕过 Java 访问控制规则，javac 不认。需要类似效果时改用反射 + setAccessible(true)。
🔧 现代化写法

本章例子在仓库里用的是 AspectJ 1.6 + 老版 org.codehaus.mojo:aspectj-maven-plugin（source/target 1.5）。 现在写同样的代码，pom.xml 建议这样配置：

pom.xml（现代等价写法）
<properties>
    <maven.compiler.release>17</maven.compiler.release>
    <aspectj.version>1.9.22</aspectj.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.aspectj</groupId>
        <artifactId>aspectjrt</artifactId>
        <version>${aspectj.version}</version>
    </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
        <groupId>dev.aspectj</groupId>                 <!-- 社区维护的现代分支 -->
        <artifactId>aspectj-maven-plugin</artifactId>
        <version>1.14</version>
        <configuration>
            <complianceLevel>17</complianceLevel>
            <source>17</source>
            <target>17</target>

            <parameters>true</parameters>             <!-- 取代老式 -g:vars -->
        </configuration>
        <executions>
            <execution>
                <goals><goal>compile</goal><goal>test-compile</goal></goals>
            </execution>
        </executions>
    </plugin>
  </plugins>
</build>
⚠️ 版本提醒

org.codehaus.mojo:aspectj-maven-plugin 已多年未更新且不支持新版 Java；社区分支 dev.aspectj:aspectj-maven-plugin 才是目前活跃维护、支持 Java 17/21 的选择。使用前请到 Maven Central 确认最新版本号。

6. 该选 @AspectJ 还是传统语法？

传统语法（.aj）
  • 写法最紧凑，功能最全（ITD、异常软化都支持）
  • 必须用 ajc / AJDT 编译，普通 IDE、静态分析工具不认识
  • 适合：团队用 Eclipse + AJDT，且要重度使用 ITD 等高级特性
@AspectJ 语法（推荐默认选项）
  • 纯 Java 注解，javac / IntelliJ IDEA / 静态分析工具全部兼容
  • Spring AOP 只支持这种语法（不需要专门编译器，用代理实现）
  • 适合：几乎所有现代 Spring / Spring Boot 项目

结论：如果你在写 Spring 应用，直接用 @AspectJ 语法，第 9 章会看到 Spring AOP 怎么在不需要任何特殊编译器的情况下， 仅凭 @AspectJ 注解就能给 Bean 生成代理。只有当你真的需要 ITD、异常软化这类“结构级”能力时，才需要请出传统语法。

小结 & 自测

  • @AspectJ 语法里，一个类要变成切面，需要做什么？
    给类加上 @Aspect 注解即可；它本质上还是一个普通 Java 类，只是编译期/织入期的行为会被特殊处理。
  • 为什么 @AspectJ 语法里 if() 切点要专门处理，不能直接把条件表达式写在字符串里？
    因为切点表达式是字符串，javac 不会检查字符串内部的拼写/语法错误；把条件逻辑放进一个真正的 Java 方法体里，才能让 javac 帮你在编译期发现错误。
  • around 通知里，@AspectJ 语法用什么代替传统语法的 proceed() 关键字？
    声明一个 ProceedingJoinPoint 类型的方法参数，调用它的 proceed()（或 proceed(Object[])）方法。
  • 下面三个功能里，哪个可以用 @AspectJ 语法实现：① 给已有类新增字段 ② 声明编译期警告 ③ 特权访问私有字段？
    只有 ②——用 @DeclareWarning 标注一个 static final String 字段。①③ 都需要传统语法。
  • 为什么 @AspectJ 切点表达式里的类型名必须写全限定名（比如 java.sql.Connection 而不是 Connection）？
    因为 import 语句只是源码层面的写法糖，编译成字节码后不会保留；切点表达式是注解里的字符串，织入器读到的是编译后的字节码，没有 import 信息可用。
