CHAPTER 10

监控类切面

一句话概括本章：日志追踪、异常记录、性能计时——这些"到处都要抄一遍"的代码，用一个切面写一次就够了。

本章你将学到

  • 方法调用链追踪（entry/exit tracing），以及如何用缩进体现调用深度
  • 用 around 通知统一实现异常监控和性能计时
  • NDC/MDC 上下文日志的作用，以及它在现代 Java 生态里的替代品

1. 问题：日志代码"长得一模一样"，却散落在每个方法里

如果你写过企业应用，大概率见过这种代码：每个 Service 方法开头一句 logger.info("Entering xxx")， 结尾再来一句 logger.info("Exiting xxx")，性能敏感的地方再包一层计时。 这些代码逻辑完全相同，只是方法名不同——典型的"横切关注点"。

图 10-1　把重复的追踪/日志代码从各个业务方法中"抽出来"，集中到一个切面

2. 方法调用链追踪：用缩进体现调用深度

最基础的追踪切面只需要在方法进入/退出时打印一行日志。但如果 A 调 B、B 又调 C，日志全部堆在一起会很难看出层级关系。 书中的做法很巧妙：用 Log4j 的 NDC（Nested Diagnostic Context，嵌套诊断上下文）在每层调用时 push 一个空格，退出时 pop 掉——这样每深一层调用，日志就自动多一个缩进。

图 10-2　每进入一层方法调用就 push 一次缩进，退出时 pop 掉，日志天然呈现调用树形结构

对应仓库 ch10/workspace/Section10.4.2SharingTracingAspect 里的可复用缩进切面：

IndentationTraceAspect.aj（书中原版，Log4j 1.x + AspectJ 原生语法）
public abstract aspect IndentationTraceAspect {
    private Logger logger = Logger.getLogger(IndentationTraceAspect.class);

    public abstract pointcut traced();

    before() : traced() {
        Signature sig = thisJoinPointStaticPart.getSignature();
        logger.log(Level.INFO, "Entering [" + sig.toShortString() + "]");
        NDC.push(" "); // 每进一层，缩进 +1
    }

    after() : traced() {
        NDC.pop(); // 退出时把缩进弹回去
    }
}
书中写法（已过时）
  • Log4j 1.x：org.apache.log4j.Logger / NDC
  • AspectJ 原生 .aj 语法（abstract aspect + abstract pointcut）
推荐的现代写法
  • SLF4J + Logback，org.slf4j.MDC 替代 NDC（键值对形式，比栈式 NDC 更灵活）
  • @AspectJ 注解语法，抽象切面用 @Aspect abstract class
IndentationTraceAspect.java（现代化：SLF4J + MDC + @AspectJ 语法）
@Aspect
public abstract class IndentationTraceAspect {
    private static final Logger log = LoggerFactory.getLogger(IndentationTraceAspect.class);
    private static final ThreadLocal<Integer> DEPTH = ThreadLocal.withInitial(() -> 0);

    @Pointcut
    public abstract void traced();

    @Before("traced()")
    public void before(JoinPoint jp) {
        int depth = DEPTH.get();
        MDC.put("indent", "  ".repeat(depth)); // MDC 放到日志 pattern 的 %X{indent} 里
        log.info("Entering [{}]", jp.getSignature().toShortString());
        DEPTH.set(depth + 1);
    }

    @After("traced()")
    public void after() {
        DEPTH.set(DEPTH.get() - 1);
    }
}
🔧 现代生态里，这一章的活谁在干？

在单体应用里，AspectJ + SLF4J/MDC 依然是给日志加"结构化上下文"最干净的办法——业务代码里完全看不到日志痕迹。 但如果你的系统是微服务，跨服务的调用链追踪现在通常交给 Micrometer Tracing + OpenTelemetry 这类分布式追踪方案（它们会自动传播 traceId/spanId，跨进程也能串起调用链， 这是本章手写的 NDC 缩进方案做不到的）。切面在这里的角色变成了：把 traceId 之类的上下文塞进业务日志， 而不是自己发明一套追踪机制。

3. 性能监控：用 around 通知量时间

追踪解决的是"发生了什么"，性能监控解决的是"花了多久"。因为要同时拿到方法执行前后的时间戳，天然要用能包住整个方法执行过程的 around 通知（见仓库 ch10/workspace/Section10.8PerformanceMonitoring）：

AbstractPerformanceMonitoringAspect.java（书中原版逻辑，现代化为 SLF4J）
@Aspect
public abstract class AbstractPerformanceMonitoringAspect {
    private static final Logger log = LoggerFactory.getLogger(AbstractPerformanceMonitoringAspect.class);

    @Pointcut
    public abstract void monitoredOp();

    @Around("monitoredOp()")
    public Object monitor(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try {
            return pjp.proceed(); // 真正执行原方法
        } finally {
            long elapsed = System.nanoTime() - start;
            log.info("{} took {} ns", pjp.getSignature().toShortString(), elapsed);
        }
    }
}
💡 为什么用 finally

把计时和日志放进 finally 块，无论目标方法正常返回还是抛异常，耗时都会被记录下来—— 这正是 around 通知比 before + after returning 组合更适合计时场景的原因： 它能拿到"进入"和"离开"（无论何种方式离开）之间完整的时间窗口。

4. 异常监控：把 try/catch 的"打印日志"部分抽走

很多项目里几乎每个方法都写着 catch (Exception e) { logger.error(...); throw e; }。 用 @AfterThrowing 通知可以把这段"记录异常"的逻辑收敛到一处，业务代码只需要专心处理业务异常， 不用再操心"打没打日志"。

小结 & 自测

  • 为什么追踪日志天然适合用切面实现，而不是每个方法手写？
    因为追踪代码在所有方法里逻辑完全相同（都是"进入时打印+退出时打印"），是典型的横切关注点，用切面写一次即可应用到所有匹配的方法。
  • 缩进式调用链追踪的核心技巧是什么？
    用 before 通知在每次进入方法时增加一层缩进（书中用 Log4j NDC.push，现代写法可以用线程本地的深度计数器配上 SLF4J MDC），after 通知里再把缩进减一层。
  • 性能监控为什么用 around 通知而不是 before/after？
    因为需要同时拿到方法执行前后的时间戳来计算耗时，around 通知能包裹住整个方法执行过程，并且可以放在 finally 里保证异常时也能记录耗时。
  • 在分布式微服务场景下，本章的追踪思路有什么局限？
    NDC/MDC 缩进只能反映单个进程内的调用层级，无法跨进程/跨服务传播；跨服务的调用链追踪需要 OpenTelemetry / Micrometer Tracing 这类分布式追踪方案。
