第 1 章

发现 AOP

一句话概括本章：面向对象编程（OOP）能把“业务功能”模块化得很好，但对日志、权限、事务这类“横切关注点”无能为力——AOP 就是为了解决这个缺口而生的。

本章你将学到

  • 什么是“横切关注点”（crosscutting concern），它为什么是 OOP 的老大难问题
  • “代码纠缠”（tangling）与“代码分散”（scattering）这两个症状怎么识别
  • AOP 引入的新武器：切面（aspect）、连接点（join point）、切点（pointcut）、通知（advice）
  • AOP 不是银弹：它的成本、收益，以及什么时候该用

1. 一个你多半已经踩过的坑

如果你写过任何一个稍微像样的后端服务，大概率写过这样的代码：某个 OrderService 方法里，业务逻辑只有五行，但方法头尾却挂着一堆“杂事”——记录日志、检查权限、开启事务、捕获异常上报监控。 业务逻辑被这些“杂事”前后包夹，一个方法看起来像三明治。

书里把系统的功能拆成两类：核心关注点（core concern，比如“下单”“查库存”这些业务本身）和 横切关注点（crosscutting concern，比如日志、安全、事务、缓存、性能监控）。核心关注点很适合用类和接口来模块化—— OrderService 就该只管下单。但横切关注点很“不讲武德”：它不属于任何一个模块，却同时出现在几乎所有模块里。

2. 两个症状：代码纠缠 & 代码分散

书中用两个术语精确描述了这个坏味道：

  • 代码纠缠（tangling）：一个方法内部，核心逻辑和日志/权限/事务代码绞在一起，你必须从一堆“杂事”里找到真正的业务逻辑。
  • 代码分散（scattering）：同一个关注点（比如“检查权限”）的实现代码，散落在几十个不同的类里。哪天权限校验逻辑要改，你得改几十个地方。
💡 类比：CSS 与 HTML

没有 CSS 之前，HTML 标签上到处塞 <font color="red">，内容和样式纠缠在一起，改个颜色要改一百个页面。 CSS 用“选择器 + 样式规则”把样式从内容里分离出来。
AOP 做的是同一件事，只不过对象从“网页元素”换成了“程序里的方法调用”：切点（pointcut）就是选择器，通知（advice）就是样式规则。

3. AOP 的解法：把关注点“焊”回去

AOP 并不是说横切代码不用写了——认证逻辑总要有人实现。AOP 做的是把这些逻辑放进一个新的模块单元，叫 切面（aspect），然后由一个叫织入器（weaver）的工具，在编译期、类加载期或运行期， 把切面“焊接”回业务代码要生效的地方。业务类本身完全不知道切面的存在。

要理解后面所有章节，先记住 AOP 世界里的四个核心词——第 2、3 章会逐一细讲，这里先建立直觉：

术语直觉理解
连接点 join point程序执行过程中“发生的事情”，例如某个方法被调用、某个异常被抛出
切点 pointcut一条“查询语句”，从所有连接点里挑出你关心的那些（“所有 public 方法”“所有带 @Transactional 的方法”）
通知 advice命中切点后要执行的代码——之前执行、之后执行，还是把原方法包起来执行
切面 aspect把上面几样打包在一起的模块，相当于 AOP 世界里的“类”

4. 你其实已经在用 AOP 了

书里在 2009 年举的例子是 EJB3 拦截器，放到今天，更贴近的例子是这些你可能天天在用的 Spring 特性——它们背后全部是同一套 AOP 模型：

日常代码里“隐形”的切面
@Transactional
public void placeOrder(Order order) { ... }

@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) { ... }

@Cacheable("products")
public Product findById(Long id) { ... }

这三行注解背后，Spring 分别用一个“事务切面”“安全切面”“缓存切面”，在方法执行前后悄悄插入了开事务/提交回滚、鉴权、读写缓存的逻辑—— 你的 placeOrder 方法体里一行这些代码都不用写。等到第 9 章，你会看到 Spring 是怎么做到这一点的（提示：靠动态代理）。 另外像 Micrometer/OpenTelemetry 的自动埋点、日志框架的 MDC 追踪，本质上也是同一个思路。

5. AOP 不是免费的午餐

书中很诚实地讨论了 AOP 的代价，这点在 2026 年依然成立：

⚠️ 使用 AOP 前要知道的事

1）学习曲线：切面代码不在调用现场，刚接触时你会看着一段代码却不知道背后发生了什么“魔法”；
2）调试更绕：报错堆栈会经过代理类/织入生成的方法，需要适应；
3）团队协作成本：滥用 AOP（尤其是过于宽泛的切点表达式）会让代码行为变得难以预测。
好消息是：现代 IDE（IntelliJ IDEA 对 Spring AOP 有很好的“哪个切面生效了”提示）已经比 2009 年友好太多。

换来的收益也很实在：核心业务代码不再被“杂事”污染，改一个横切逻辑只需要改一个切面而不是几十个类， 新增一个横切需求（比如给某类接口加限流）往往可以“无侵入”地插入，不用动原有代码——这正好呼应了敏捷开发里的 YAGNI 原则。

✏️ 动手练习（思考题，无需写代码）

打开你现在参与的任意一个项目，随便挑一个 Service 类，数一数方法体里有多少行是「真正的业务逻辑」， 多少行是日志/权限/事务/异常处理这类横切代码。这个比例，就是 AOP 想帮你优化的地方。

小结 & 自测

  • 什么是“横切关注点”？举两个例子。
    同时影响系统里多个不相关模块、无法被单一模块干净封装的功能，例如日志记录、权限校验、事务管理、缓存、性能监控。
  • 代码纠缠和代码分散有什么区别？
    纠缠指“一个方法内部”核心逻辑和横切逻辑混在一起；分散指“同一个横切逻辑”的代码重复出现在很多个方法/类里。两者通常同时出现。
  • AOP 中“织入”（weaving）是在做什么？
    把切面里定义的横切逻辑，按照切点规则插入到业务代码要生效的具体位置，生成最终真正运行的程序（可以发生在编译期、类加载期或运行期）。
  • Spring 的 @Transactional 和 AOP 有什么关系？
    它是 AOP 思想在 Spring 里的一个具体应用：Spring 用一个内置的事务切面，在被 @Transactional 标注的方法执行前后自动插入开启事务、提交/回滚的逻辑。
  • AOP 是不是“银弹”，用了就一定更好？
    不是。它有学习成本和调试成本，切点写得过于宽泛还会让程序行为难以预测。应该在“横切逻辑确实分散在很多地方”时引入，而不是为了炫技滥用。
