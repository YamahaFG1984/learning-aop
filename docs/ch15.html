第 15 章

应用安全

一句话概括本章：认证（你是谁）和授权（你能干什么）本质上都是"在方法执行前插一段检查代码"——这正是切面最擅长的事。本章带你从零手写一遍安全切面，再看懂 Spring Security 现在是怎么用切面帮你把这些活都干了的。

本章你将学到

  • 认证（Authentication）与授权（Authorization）的区别，以及为什么它们都是横切关注点
  • 如何手写一个认证切面 + 授权切面，理解 Spring Security 底层的工作原理
  • 用注解驱动授权（@Secured / @PreAuthorize）
  • 字段级权限控制——以及为什么这必须用完整的 AspectJ，Spring AOP 做不到

1. 认证 ≠ 授权

很多初学者会把这两个词混着用，但它们是两件完全不同的事：认证（Authentication）回答"你是谁"——通常是核验用户名密码； 授权（Authorization）回答"你能不能做这件事"——比如只有 ADMIN 角色才能删除商品。 一次请求通常要先过认证，再过授权，两道关卡都得通过才能真正执行业务方法。

💡 类比

把安全检查想象成进大楼：门口保安核对你的工牌确认"你是公司员工"（认证），电梯里的门禁卡读卡器再判断"你能不能刷到 8 楼的机房"（授权）。这两道关卡分别由两个独立的"检查员"（切面）负责，业务楼层里的人完全不需要关心保安是怎么工作的。

2. 从零手写认证 & 授权切面

书中在 ch15/workspace/Section15.4.1ImplementingAuthenticationAspect 里演示了一个思路： 把"要不要认证""在哪认证"这些决策做成一个抽象切面，具体的选点逻辑交给子切面决定——这其实就是第 6 章讲过的抽象切面模式。

ajia/security/AbstractAuthenticationAspect.java（书中写法，字段类型微调后仍可用）
@Aspect
public abstract class AbstractAuthenticationAspect {
    private AuthenticationSupport authenticationSupport;

    @Pointcut
    public abstract void authenticationRequired();  // 交给子切面定义“在哪拦”

    @Before("authenticationRequired()")
    public void authenticate() {
        authenticationSupport.authenticate();        // 具体怎么认证，交给支持类
    }
    // setter 省略
}

授权切面的结构几乎一样，只是把 authenticate() 换成 authorize(JoinPoint jp)， 因为授权要知道"当前访问的是哪个连接点"，才能查出这个方法需要什么角色。书中给了两种选点方式：

选点方式做法优点缺点
不用注解 execution(* ajia.service..*.*(..)) 按包名匹配 业务代码零侵入 安全规则藏在切点表达式和外部映射表里，不直观、易碎
用注解 @Secured("ROLE_SUPERVISOR") 标在类/方法上 规则和代码放在一起，一目了然 业务类多了一个安全相关的注解依赖

3. 今天怎么做：Spring Security 的方法级安全

书里手写的这套"切点 + 支持类 + AccessDecisionManager"，正是 Spring Security 方法安全的工作原理—— 没错，Spring Security 的 @Secured / @PreAuthorize 本身就是靠 Spring AOP 实现的一个 Advisor。 回忆一下第 9 章讲的"Spring AOP 只能代理 Spring 容器管理的 Bean"：这正是为什么方法级安全默认只能保护 Service 层的 Bean，而管不到用 new 创建的领域对象。

书中写法（已过时）
  • 手写 AbstractAuthenticationAspect / AbstractAuthorizationAspect
  • XML 配置 <security:authentication-manager>，factory-method="aspectOf"
  • 旧版 Spring Security（Acegi 血统）
推荐的现代写法
  • Spring Boot 3.x + Spring Security 6.x
  • @EnableMethodSecurity 开启方法级安全
  • @PreAuthorize("hasRole('SUPERVISOR')") 用 SpEL 表达式直接写在方法上
现代等价写法：无需自己写切面
@Configuration
@EnableMethodSecurity // Spring Security 6.x：默认已支持 @PreAuthorize/@PostAuthorize
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults())
            .build();
    }
}

// 业务类：完全不需要手写切面，也不用配置 XML
@Secured("ROLE_SUPERVISOR") // 或者更推荐用下面这行
@PreAuthorize("hasRole('SUPERVISOR')")
public void expireProduct(Product product) { ... }
⚠️ 版本提醒

Spring Security 5 之前依赖 GlobalMethodSecurityConfiguration + @EnableGlobalMethodSecurity，这个注解在 Spring Security 6 中已被废弃， 统一改为 @EnableMethodSecurity。@Secured/@RolesAllowed 仍然可用， 但官方推荐优先使用支持 SpEL 表达式的 @PreAuthorize/@PostAuthorize，可以写更灵活的规则，例如书中 15.6.2 节提到的"只有部门经理才能操作本部门商品"： @PreAuthorize("#product.department.manager.name == authentication.name")。

4. 字段级权限：为什么 Spring AOP 做不到

书中 15.5 节举了一个很好的例子：医疗系统里，保险专员能看到"某项检查做过没有"，但看不到具体的检查结果——这是字段级的权限，而不是方法级或对象级。 Spring AOP 基于 JDK 动态代理 / CGLIB，本质上是在对象外面套一层壳，只能拦截"从外部调用某个公开方法"这件事，根本看不到、也拦不住对字段的直接读写。 要做到字段级拦截，必须用完整的 AspectJ 编译期/加载期织入，直接在字节码层面改写字段访问指令。

ajia/security/AccessFieldSecurityAspect.java（书中写法，思路不过时，只需升级依赖包名）
@Aspect
public class AccessFieldSecurityAspect {
    private AuthorizationSupport securitySupport;

    @Pointcut("(get(@Access * *) || set(@Access * *)) && @annotation(access)")
    public void secureFieldAccess(Access access) {}

    @Before("secureFieldAccess(access)")
    public void secure(Access access) {
        securitySupport.authorize(access);   // get/set 之前先查权限
    }
}

// 领域对象里只需要一个注解
public class Product {
    @Access("ROLE_SUPERVISOR") private double price;
}
🔧 现代化提示

这套字段级拦截思路本身没有过时，只是原书用的 org.springframework.security.access.vote.* 包在 Spring Security 6 中已重构（例如 AccessDecisionManager 体系已被更灵活的 AuthorizationManager<T> 取代），迁移时建议实现新的 AuthorizationManager 接口而不是继续用旧的 Voter 体系。 至于 AspectJ 编译/织入部分，直接沿用 dev.aspectj:aspectj-maven-plugin 即可，语法完全兼容。

✏️ 动手练习

打开仓库 ch15/workspace/Section15.5ImplementingFieldLevelAuthorization，跑一下 AccessFieldSecurityAspectTest。 然后试着给 Product 类再加一个 @Access("ROLE_ADMIN") 标注的字段，观察不同角色访问时的行为差异——体会一下"同一个对象，对不同调用方展现不同的可见性"。

小结 & 自测

  • 认证和授权分别回答什么问题？
    认证回答"你是谁"（身份核验）；授权回答"你能不能做这件事"（权限判断）。一次请求通常先认证后授权。
  • 为什么说 Spring Security 的方法安全"本质上就是 AOP"？
    因为 @PreAuthorize 等注解正是通过 Spring AOP 给 Bean 生成代理、在代理里插入一段权限检查逻辑实现的，和书中手写的授权切面是同一套原理。
  • 为什么字段级权限控制不能用 Spring AOP 实现，必须用完整的 AspectJ？
    Spring AOP 基于代理，只能拦截"从代理外部调用某个公开方法"；字段的读写不经过方法调用，代理感知不到。完整 AspectJ 通过织入直接修改字节码里的 getfield/putfield 指令，所以能拦截字段访问。
  • 书中的 factory-method="aspectOf" 配置是做什么用的？现代 Spring 还需要吗？
    当切面由 AspectJ 织入器创建（而不是 Spring 容器 new 出来）时，要通过 aspectOf() 静态方法拿到切面的单例实例再注入依赖。如果改用纯 Spring AOP（@Aspect + @EnableAspectJAutoProxy），切面本身就是一个普通 Bean，不需要这个配置。
  • 现代 Spring Security 推荐用 @PreAuthorize 还是 @Secured？
    推荐 @PreAuthorize，因为它支持 SpEL 表达式，可以写出比"某个角色"更复杂的规则（比如结合方法参数判断）；@Secured 只能声明角色，功能更受限，但配置更简单。
