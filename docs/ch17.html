迈出下一步

一句话概括本章：AOP 不是“要不要用”的选择题，而是“从哪里开始、走多快”的节奏问题。本章给你一条从零风险到核心业务的落地路线图。

本章你将学到

  • 一条循序渐进的 AOP 采纳路径：先低风险，再核心业务
  • “开发期切面” vs. “生产期切面”的区别
  • 怎么判断一个功能是不是横切关注点、该不该用切面实现
  • 2026 年的现实：AOP 早已“隐身”在你每天用的框架注解背后

1. 先热身，再上场：采纳路径

本书作者的建议其实很朴素：不要一上来就用切面改造核心业务逻辑。 应该像学游泳先在浅水区扑腾一样，从风险最低、影响面最小的场景开始练手， 等团队对“切面会在什么时候生效、会不会误伤其他代码”有了直觉之后， 再逐步把 AOP 用到事务、安全这类“一旦出错就是生产事故”的领域， 最后才是最难判断的——核心业务规则本身有没有横切逻辑。

💡 类比

这就像学开车不会直接上高速：先在空地练手感（日志/追踪切面，随时能删掉，不影响发布）， 再上市区道路（缓存/监控，出错影响可控），最后才敢跑高速和复杂路况（事务/安全/核心业务规则）。

2. 开发期切面 vs. 生产期切面

书里把切面分成两大类，这个分类到今天依然很实用：

类型特点典型场景
开发期切面 只在开发/测试阶段启用，随时可以整体移除，不进入生产构建 调试并发问题的追踪日志、性能画像、编码规范检查、模拟故障做容错测试
生产期切面 是系统正确性的一部分，必须始终存在，不能“可选关闭” 事务管理、安全校验、并发控制

开发期切面几乎零风险——它们不出现在发布包里，出了问题大不了删掉重来； 生产期切面则需要认真设计、充分测试，因为它们和事务、安全一样，一旦漏掉就是真实的线上问题。 建议的路径就是：先在开发期切面上建立信心，再挑战生产期切面。

3. 怎么判断“这是不是横切关注点”

书中给出一个非常好用的自检清单，放到今天依然成立：

  • 会不会导致代码散布（scattering）？ 同样的几行代码要在几十个地方重复粘贴 → 强烈信号。
  • 会不会导致代码纠缠（tangling）？ 哪怕只有一处调用，业务逻辑和另一件事（比如加锁）混在一个方法体里，读起来就很累 → 也值得用切面分离。
  • 警惕“拿切面去打补丁”：如果一个方案的本质是绕过某个设计缺陷而不是解决它，宁可先重构，别急着写切面。

判断之后落地也有一个稳妥的三步走：先做一遍传统实现（哪怕只是草稿，帮你想清楚设计）， 再把切面限制在小范围（比如只对某个包生效），验证没问题后再放开到全局。

4. 2026 年的现实：AOP 早就“隐身”在你身边

本书写于 Spring 2.x/3.x 的年代，那时候“要不要引入 AOP”还是一个需要向团队/管理层申请的决定。 今天的情况完全不同：只要你在用 Spring Boot，你每天都在用切面，只是没意识到而已。 @Transactional、@Cacheable、 @Async、@PreAuthorize、 Micrometer 的 @Timed，甚至 Mockito 生成 mock 对象， 背后全部是代理（proxy）或字节码增强这类 AOP 机制在工作。

所以，2026 年学“怎么落地 AOP”，很大一部分其实变成了：

  • 先看懂框架已经帮你做的事——理解 @Transactional 之类注解背后是代理机制，出问题时才知道去哪排查（参见第 9、14 章）；
  • 框架覆盖不到的地方，才是原生 AspectJ 的舞台：比如要给不是 Spring Bean 的普通对象（领域对象、第三方库的类）织入行为，要做团队自定义的编码规范检查（第 11 章），或者要修改你不拥有源码的 jar 包（附录 B/C）。这些场景 Spring AOP 的“只能代理 Spring Bean 的公开方法”这条限制帮不上忙，需要请出完整的 AspectJ 织入器。
🔧 一句话总结全书

横切关注点（日志、事务、安全、缓存、并发……）本来就散落在系统各处； AOP 给了你一个专门的模块化单位——切面——把它们收拢起来。 不管你是直接写 @Aspect，还是只是在方法上标一个 @Transactional， 本质上都是在使用同一套思想。理解了这一点，你就已经从“会用 AspectJ”升级成了“懂 AOP”。

✏️ 动手练习（没有代码，用脑子跑一遍）

回顾你手头正在维护的一个真实项目：有没有某个逻辑（日志格式统一、参数校验、埋点、限流、多语言……） 是“散布”在很多个类/方法里，或者跟业务代码“纠缠”在一起、让人读起来很累的？ 用本章的自检清单判断一下：这算不算横切关注点？如果是，你会先用哪种最小风险的方式（比如只在一个模块试点）去验证切面方案？

小结 & 自测

  • 为什么书里建议先从“开发期切面”入手，而不是一上来就改造核心业务？
    开发期切面不进入生产构建，出问题可以直接删除重来，风险几乎为零，能帮你在低风险场景下建立起对 AOP 行为的信心和直觉，再挑战事务、安全这类必须长期存在、出错代价高的生产期切面。
  • 判断一个功能是不是“横切关注点”，可以看哪两个信号？
    代码散布（同样的代码在很多地方重复出现）和代码纠缠（业务逻辑和另一件不相关的事混在同一段代码里，哪怕只有一处调用）。出现任一信号，都值得考虑用切面分离。
  • 为什么说 Spring Boot 开发者“每天都在用 AOP，只是没意识到”？
    因为 @Transactional、@Cacheable、@Async、@PreAuthorize 等常用注解，底层都是靠 Spring AOP 生成的代理对象在方法调用前后插入逻辑，本质就是切面，只是框架把“写切面”这一步替你做好了。
  • 什么时候 Spring AOP（基于代理）不够用，必须上原生 AspectJ？
    当需要给非 Spring Bean 的普通对象织入行为、需要在编译期做设计规范检查、或者需要织入你没有源码的第三方 jar 包时，Spring AOP“只能代理 Spring 容器里 Bean 的公开方法”这条限制就不够用了，这些场景需要完整的 AspectJ 编译期/加载期织入能力。
  • 书中建议落地一个新切面时，先做哪一步来降低风险？
    先把切面的作用范围限制在小范围（例如只对某个包用 within() 限定，或只在构建配置里包含一个模块），验证没问题之后，再放开到整个系统。
