第 16 章

改善领域逻辑

一句话概括本章：前面 14 章都在用切面处理"基础设施"型的横切关注点（日志、事务、安全）；这一章反过来，教你用 AOP 把业务逻辑本身也变得更健康——让"只有 getter/setter 的贫血对象"重新长出行为。

本章你将学到

  • 什么是"贫血领域模型"，为什么它是个问题
  • 怎么用切面把 Spring 容器的依赖注入能力，扩展到 new 出来的领域对象上
  • 用类型间声明（ITD）给领域对象"充血"：把散落在 Service 里的逻辑搬回实体
  • 用切面统一实施领域级的业务规则（订单校验、聚合边界保护）

1. 贫血模型的问题：逻辑去哪了？

面向对象的初衷是"数据 + 行为绑在一起"，但现实中很多领域对象——尤其是 JPA 实体——常常沦为纯粹的数据容器：只有字段和 getter/setter， 所有计算逻辑都被塞进了 OrderService 这样的服务类。Martin Fowler 把这种现象叫做贫血领域模型（Anemic Domain Model）。

根源在于：领域对象往往由 new 或 ORM 框架反射创建，不受 Spring 容器管理，所以没法用普通的依赖注入拿到协作对象（比如一个计算折扣的 PricingStrategy）。 没有依赖，就写不出真正的业务方法，逻辑只能被迫搬到能拿到依赖的 Service 层。

💡 类比

贫血模型就像一个只会"被填表"的空白表格（Order 只有字段），所有"怎么算总价、怎么判断是否超额"的智慧都锁在另一个人（OrderService）脑子里。充血模型则是让表格自己长出计算器——你问表格"你的总价是多少"，它自己就能算出来。

2. 关键难题：怎么把依赖注入到 new 出来的对象里？

Spring 容器只管理它自己创建的 Bean。new Order() 这行代码完全绕开了容器，Spring 根本不知道这个对象存在，自然没法帮它注入 PricingStrategy。 书中给出的解法是：写一个切面，在"任何 Order 实例被创建（或反序列化）"这个连接点上插入一段依赖注入逻辑——这正是 Spring 的 @Configurable 机制的原型。

三种给领域对象做 DI 的方式

ajia/domain/Order.java（书中写法，字段类型需升级到 jakarta.persistence，见下方版本提醒）
@Entity
@Table(name = "orders")
@Configurable                       // 告诉 Spring：这不是 Bean，但也请帮它注入依赖
public class Order extends DomainEntity {

    @Autowired private transient PricingStrategy pricingStrategy;

    public double getTotalPrice() {
        return pricingStrategy.getPrice(this);   // 业务逻辑现在长在实体自己身上
    }
}

要让 @Configurable 生效，仅仅加注解不够，还需要在 Spring 配置里打开"配置感知织入"，并且用 AspectJ 织入（而不是 Spring AOP 代理）—— 因为这个切面要拦截的是"对象构造"这个连接点，Spring AOP 的代理机制根本插不进构造函数里。

书中写法（已过时）
  • XML：<context:spring-configured/>
  • javax.persistence.Entity
  • 需要在 pom.xml 里手动接入 AspectJ 编译期/加载期织入
推荐的现代写法
  • @EnableSpringConfigured（等价的 Java 配置）
  • jakarta.persistence.Entity（Spring Boot 3.x 起 JPA 命名空间已迁移到 Jakarta）
  • Maven 里配 spring-aspects 依赖 + dev.aspectj:aspectj-maven-plugin 做编译期织入，或用 -javaagent:spring-instrument.jar 做加载期织入
pom.xml（现代等价配置，启用 @Configurable）
<dependency>
  <groupId>org.springframework</groupId>
  <artifactId>spring-aspects</artifactId>
  <!-- 版本随 Spring Boot BOM，无需单独指定 -->
</dependency>

<plugin>
  <groupId>dev.aspectj</groupId>
  <artifactId>aspectj-maven-plugin</artifactId>
  <configuration>
    <aspectLibraries>
      <aspectLibrary>
        <groupId>org.springframework</groupId>
        <artifactId>spring-aspects</artifactId>
      </aspectLibrary>
    </aspectLibraries>
  </configuration>
</plugin>
🔧 现代化提示

@Configurable 至今仍是 Spring 官方功能，是本章"依赖注入织入切面"思想最直接的延续，主要用在 JPA 实体这类不得不由持久化框架而不是 Spring 创建的对象上。 但要注意：如今更主流的做法是尽量让领域对象保持"纯粹"——不依赖 Spring，通过构造函数接收依赖，由充血的领域服务/工厂方法组装（也就是 DDD 里说的"贫血 Entity + 显式的领域服务"或"真正充血但用工厂组装"两种取舍）。 像本章这样用织入把容器能力"偷渡"进 new 出来的对象，是一种更高级、更小众的技巧，日常业务代码里请优先考虑构造函数注入，只有在实体确实必须由 ORM 反射创建时才考虑 @Configurable。

3. 除了依赖注入，切面还能干什么

本章后半段展示了几个"领域逻辑用切面会更干净"的例子：

  • 库存变更监控——用 after() returning 通知在 InventoryService.addProduct/removeProduct 执行后通知监控系统，而不是在每个业务方法里手写一遍。
  • 订单级校验——用一个切面拦下所有修改 Order 的方法调用，统一跑校验规则（比如订单总额不能超限），并用 !cflow(...) 排除校验器自身的调用，避免递归。
  • 聚合边界保护——比如 LineItem 只能通过它所属的 Order 来修改，不能被 Web 层直接改动，用 @AggregateRoot/@Aggregate 注解 + 切面统一强制执行，呼应第 11 章讲过的"策略强制执行"思路。
ajia/domain/OrderValidationAspect.aj（书中写法，逻辑保持不变）
public aspect OrderValidationAspect {
    private OrderValidator orderValidator;

    public pointcut orderUpdate(Order order)
        : execution(* Order.*(..)) && this(order)
          && !cflow(execution(* OrderValidator+.*(..)));  // 排除校验器自己，防止死循环

    after(Order order) returning : orderUpdate(order) {
        orderValidator.validate(order);
    }
}
⚠️ 现代替代方案

如果你的校验规则比较简单（字段格式、非空、范围），现代 Spring 生态里首选 Jakarta Bean Validation（@NotNull、@Max 等 + jakarta.validation-api）， 配合 @Validated 即可声明式完成，不需要专门写切面。只有当校验规则涉及跨对象的复杂业务逻辑（比如本章"订单总额不能超限"这种需要查询整个聚合的规则）， 切面这种方式才真正体现优势。

小结 & 自测

  • 什么是"贫血领域模型"？它的根本原因是什么？
    指领域对象只有数据（getter/setter）没有行为，所有逻辑都被推到 Service 层。根本原因是领域对象通常由 new 或 ORM 反射创建，拿不到 Spring 容器管理的协作对象，写不出依赖它们的业务方法。
  • @Configurable 为什么必须用 AspectJ 织入而不能用 Spring AOP 代理实现？
    因为它要拦截的连接点是"对象的构造/反序列化过程"，而 Spring AOP 的代理是在对象创建完成之后包一层壳，根本没有机会介入构造过程本身；只有编译期或加载期织入能改写构造逻辑。
  • 书中用 ITD（类型间声明）把"简化版 API"加到 Order 类上，这样做比直接写在 Order.java 里有什么好处？
    可以把"面向使用便利性的辅助 API"和"核心领域逻辑"分别放在切面和类里，物理上分隔关注点，同时不需要修改原始类文件，便于按需增减。
  • !cflow(execution(* OrderValidator+.*(..))) 这段切点的作用是什么？
    排除"当前正处于 OrderValidator 及其子类方法执行过程中"的连接点，防止校验器内部对 Order 的调用又触发一次校验，导致无限递归。
  • 现代项目里，简单的字段校验（非空、范围）应该用切面还是 Bean Validation？
    优先用 Jakarta Bean Validation 的注解（如 @NotNull），声明式且是行业标准；只有涉及跨字段/跨对象的复杂业务规则时才考虑专门写校验切面。
