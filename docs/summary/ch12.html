CHAPTER 12

切面设计模式

一句话概括本章：三种"老手才知道"的切面写法——worker object（工人对象）、wormhole（虫洞）、participant（参与者）——帮你解决普通切点/通知搞不定的问题。

本章你将学到

  • Worker object 模式：让切面把"要执行的操作"打包成一个对象，方便丢给线程池、事务管理器等别的地方去执行
  • Wormhole 模式：不改任何中间方法的参数列表，把调用链最上层的上下文"直接传送"到最下层
  • Participant 模式：当"方法名/类型"不足以描述某种业务特征时，让类主动"报名参与"某个切面行为

1. Worker object 模式：把一次调用"打包"成对象

设想一个需求：把某些耗时操作（缓存预取、项目备份）扔到线程池里异步执行，而不是阻塞当前调用线程。 如果不用切面，你得给每个耗时方法手写一个 Runnable 包装类，改造所有调用点——费时又容易漏改。

Worker object 模式的思路是：用 around 通知把"原本要执行的连接点"包进一个匿名 Runnable， 这个 Runnable 的 run() 方法里调用 proceed()。这样切面就把"何时执行/在哪里执行"这件事， 从"立刻同步执行"变成了"生成一个可以传递、可以延后执行的对象"。

图 12-1　Worker object 模式：around 通知把 proceed() 包进一个可传递的 Runnable
ch12/workspace/Section12.1.3TheWorkerObjectPatternTemplate（现代 @AspectJ 写法）
@Aspect
public class AsynchronousExecutionAspect {
    private final Executor executor = Executors.newVirtualThreadPerTaskExecutor(); // Java 21 虚拟线程

    @Pointcut("execution(* ajia.example.CachePreFetcher.fetch()) || "
              + "execution(* ajia.example.ProjectSaver.backupSave())")
    public void asyncOperation() {}

    @Around("asyncOperation()")
    public void routeAsync(ProceedingJoinPoint pjp) {
        Runnable worker = () -> {
            try { pjp.proceed(); }
            catch (Throwable t) { throw new RuntimeException(t); }
        };
        executor.execute(worker);
    }
}
💡 为什么不直接用组合/嵌套类实现，而要靠 ITD？

本章其它例子里，worker 对象常常是切面通过类型间声明（ITD，见第 5 章）引入到目标类里的一个协作对象， 而不是每次都在方法体里 new 一个匿名类。这样切面既能"生产"一个干净的领域对象供 worker 使用， 又不会把线程/回调相关的技术细节污染到业务类的源码里——业务类完全不知道自己被"安排"进了异步执行。

书中还展示了如何从 worker 里取到返回值：让 worker 类保存一个 returnValue 字段， run() 里执行 setReturnValue(proceed())， 执行完毕后 advice 再 return worker.getReturnValue()—— 对照仓库里的 Section12.1.4GettingReturnValueWithoutAspects（手写样板代码）和 Section12.1.4GettingReturnValueWithAspects（用切面统一处理）两个文件夹，能直观看出省了多少重复代码。

🔧 现代化提示

书中用 Executors.newCachedThreadPool()；在 Java 21+ 上， 对这种"发射后不管/短生命周期"的异步任务，可以直接换成 Executors.newVirtualThreadPerTaskExecutor()（虚拟线程）， 不需要担心线程池大小调优。如果需要拿到返回值并支持组合/超时，CompletableFuture 通常比手写 Worker + wait 更省心， 但理解 worker object 模式，能帮你看懂 Spring 事务管理、异步执行等框架底层是怎么用 AOP 拼出来的。

2. Wormhole 模式：跳过中间层直接传递上下文

设想一个审计需求：无论是 ATM、柜台还是网银发起的转账，最终都要落到 Account.credit()/debit()， 但记账时需要知道"这笔操作最初是从哪个渠道发起的"。如果不用切面，要么给 Account 的每个方法加一个 TransactionSystem 参数（一路传下去，污染 API），要么用 ThreadLocal 手动存取（容易忘记清理，线程池环境下还有脏数据风险）。

Wormhole 模式用 cflow() 切点，把"调用链最上层的上下文"直接和"调用链最下层的连接点"连在一起， 中间隔着多少层方法调用都无所谓。

图 12-2　wormhole 模式：借助 cflow()，跳过 B、C、D 三层，把最上层调用者的上下文直接带到最下层的通知里
wormhole 模式模板（现代 @AspectJ 写法）
@Aspect
public class AccountTransactionAudit {

    @Pointcut("execution(* ajia.banking.TransactionSystem+.*(..)) && this(ts)")
    public void transactionSystemUsage(TransactionSystem ts) {}

    @Pointcut("execution(* Account.credit(float)) && this(account) && args(amount)")
    public void accountTransaction(Account account, float amount) {}

    @Before("cflow(transactionSystemUsage(ts)) && accountTransaction(account, amount)")
    public void audit(TransactionSystem ts, Account account, float amount) {
        // 不管 A 到 credit() 之间隔了几层，这里都能拿到最初发起方 ts
        log.info("channel={} account={} amount={}", ts, account, amount);
    }
}
⚠️ 只有真正的 AspectJ 织入才能用

因为依赖 cflow()，wormhole 模式无法用 Spring AOP（代理式）实现。 Spring AOP 环境下想要类似效果，通常退回到 ThreadLocal， 或者用可观测性框架自带的传播机制（例如分布式追踪里的 TraceContext/MDC 传递，本质也是一种"虫洞"）。

3. Participant 模式：让类"报名参与"

有些横切关注点没法只靠方法名/类型模式选出来——比如"哪些操作算慢操作，需要显示等待光标"， Analytics.monteCarloSimulation() 慢，但慢不慢跟方法名毫无关系。 如果把所有"慢方法"死记硬背地列进一个大切点，一旦有新方法加入就得记得去改切面，非常脆弱。

Participant 模式反过来：让每个类自己声明"我有哪些慢方法"（通过类里内嵌的切点）， 切面只负责统一收集所有类"报名"的切点，然后套用同一套通知逻辑。类和切面通过一个共同的"角色"（切点名字或标记接口）来协作。

图 12-3　participant 模式：每个类自己"报名"哪些方法慢，切面不需要知道具体是谁
类里声明自己的切点（供切面收集）
public class Analytics {
    // 类自己最清楚哪些方法慢，由类来声明，而不是让切面死记硬背
    public pointcut slowOperation()
        : execution(* Analytics.monteCarloSimulation())
          || execution(* Analytics.updateDatabase());
}

public aspect WaitCursorManagementAspect {
    pointcut allSlowOperations() : Analytics.slowOperation() || Document.slowOperation();

    before() : allSlowOperations() { WaitCursor.set(); }
    after()  : allSlowOperations() { WaitCursor.unset(); }
}

书中还提到一种改进版——"注解驱动的 participant 模式"：与其在类里写 AspectJ 专属的 pointcut 语法， 不如让类的方法标一个 @SlowOperation 注解，切面用 @annotation(SlowOperation) 统一匹配。 这样类完全不需要引入 AspectJ 语法依赖，纯注解就能"报名参与"，这也是第 13、16 章并发控制和领域逻辑里反复用到的手法。

小结 & 自测

  • worker object 模式解决的核心问题是什么？
    把"执行某个连接点"这件事从一次性、同步的方法调用，变成一个可以传递、可以延后、可以交给别的执行环境（线程池、事务管理器等）处理的对象。
  • wormhole 模式和普通的层层传参相比，优势和代价分别是什么？
    优势是不用修改中间每一层方法的签名，加新的上下文字段也不影响中间层 API；代价是它依赖 cflow()，只能在真正的 AspectJ 织入下使用，且会让"数据是怎么传过来的"变得不那么直观，需要良好的文档和命名来弥补可读性。
  • participant 模式为什么比"把所有匹配条件写进一个大切点"更健壮？
    因为特征相关的知识（比如"这个方法慢不慢"）被放回了最了解它的类自己身上，新增类只需要自己声明参与，而不需要回头修改中心切面，避免了类和切面之间的紧耦合和遗漏风险。
  • 为什么 wormhole 模式没法用 Spring AOP 实现？
    因为它依赖 cflow() 切点来判断"当前调用是否发生在另一个连接点的控制流中"，而 Spring AOP 是基于动态代理的运行时拦截，没有 AspectJ 织入器那样对完整调用链的静态分析能力。
  • 今天写"报名参与"式的代码，为什么更推荐用注解而不是 AspectJ 原生的 pointcut 语法？
    因为标注 @SlowOperation 这样的注解，类本身不需要依赖 AspectJ 的语法/编译器，仍然是一个纯 Java 类，只有真正用到切面功能的模块才需要引入 AspectJ，耦合更松，也更容易被其它非 AspectJ 场景（比如反射框架）复用。
