CHAPTER 13

并发控制

一句话概括本章：把“哪些代码必须在特定线程上跑”“谁能同时读、谁必须独占写”这类线程安全规则，从散落在每个方法里的样板代码，收进一两个切面里统一管理。

本章你将学到

  • Swing 的“单线程规则”是什么、为什么违反它会导致诡异的 UI bug
  • 如何用一个切面自动把 UI 调用路由到正确的线程，而不用满代码库地写 invokeLater
  • 如何用 around 通知把“读写锁”模式封装成一个可复用切面
  • 这套思路怎么迁移到今天任何 GUI/服务端框架的线程封闭规则上

1. 问题：线程规则是横切关注点

Swing 有一条铁律：所有会读/写界面组件状态的代码，必须运行在“事件派发线程”（EDT, Event Dispatch Thread）上。 这不是 Swing 一家的特殊癖好——今天几乎所有 UI 框架（Android 的主线程、JavaFX 的 Application Thread、 浏览器里 DOM 只能在主线程改）都有类似规则，服务端框架里也有“不能在事件循环线程里做阻塞 I/O”这种对称的规则。

问题在于：这条规则要求你在每一处可能跨线程调用 UI 的地方，手动判断“我在不在 EDT 上”， 如果不在，就把调用包一层 Runnable 扔给 EventQueue。 书中第一个例子里，一个 Main 类在主线程里直接调用 tableModel.setValueAt(...)、JOptionPane.showMessageDialog(...) 等方法——全部违规。传统修法是把每一次调用都包进匿名 Runnable， 再手动区分“这个调用要不要阻塞等结果”（invokeLater vs. invokeAndWait）， 代码量直接翻几倍，而且极易漏改。

把 EDT 想象成餐厅里唯一能碰收银机的收银员：任何人想改账，都得把请求递给收银员去操作，而不能自己伸手进收银机。 切面就是那个自动帮你把“改账请求”递过去的传菜员——你只管正常写代码，它负责搬运。

2. AspectJ 方案：三个版本的演进

仓库对应目录：ch13/workspace/Section13.1.4SolutionAspectJWay*Version。核心是一个抽象切面 SwingThreadSafetyAspect，子切面只需要提供“哪些调用算 UI 调用”这个切点。

  • 第一版：所有匹配的调用都用 EventQueue.invokeAndWait() 同步路由——简单，但调用方全被阻塞，体验差。
  • 第二版：按返回值类型自动判断——返回 void 就异步（invokeLater），有返回值就同步。问题：showMessageDialog() 恰好返回 void，但语义上必须等用户点击「确定」，被错误地异步化了。
  • 第三版：加一个显式的 uiSyncCall() 切点，让子切面明确声明“这些方法即使返回 void 也要同步执行”——修正了第二版的语义漏洞。
ch13/workspace/Section13.1.4SolutionAspectJWayThirdVersion/.../SwingThreadSafetyAspect.aj（核心简化）
public abstract aspect SwingThreadSafetyAspect {
    public abstract pointcut uiCall();
    public abstract pointcut uiSyncCall();

    pointcut routedCall()
        : uiCall() && !within(SwingThreadSafetyAspect)
                   && !if(EventQueue.isDispatchThread());

    Object around() : routedCall() && (!voidReturn() || uiSyncCall()) {
        // 用 invokeAndWait() 同步转发，proceed() 拿到真正的返回值
    }
    void around() : routedCall() && voidReturn() && !uiSyncCall() {
        // 用 invokeLater() 异步转发
    }
}
🔧 现代化提示

书中用 .aj 原生语法 + perthis/around，在 AspectJ 1.9.x 下几乎原样能跑，只需把构建换成 Maven + dev.aspectj:aspectj-maven-plugin（目标语言级别设为 Java 17/21）。 Swing 桌面应用在今天已经小众，但同样的切面模式放到 Android（runOnUiThread）、JavaFX（Platform.runLater） 甚至 Vert.x/Netty 的 event-loop 线程封闭规则上完全成立——你只要把 uiCall() 切点换成对应框架的方法签名。 另外，Java 21 起虚拟线程（Virtual Threads）让“把耗时 I/O 移出关键线程”这件事对大部分场景变得更简单， 但它解决的是阻塞问题，不能替代“必须在某个特定线程上执行”这种线程封闭（thread-confinement）规则，两者不冲突。

3. 顺带解决：提升 UI 响应性

同一个“worker 对象模式”还能反过来用：把耗时操作自动扔到后台线程池执行，避免卡死 UI。 书中做法是定义一个 @Slow 注解，切面拦截所有标了 @Slow 的方法， 用线程池异步执行，调用方（比如按钮的点击回调）立刻返回，UI 不再卡顿。

4. 读写锁模式：另一个能被切面吃掉的并发套路

对比目录：Section13.3.1ReadWriteLockConventionalWay（传统写法） vs. Section13.3.2ReadWriteLockAspectJWay（切面写法）。 场景：一个库存缓存服务，查询（读）远比修改（写）频繁，用 ReentrantReadWriteLock 可以让多个查询并发执行，只有修改操作需要独占。

图 13-2　切面在方法执行前后加/放读锁或写锁——业务类里一行锁代码都不用写
传统写法
  • 每个方法手写 lock.readLock().lock()/unlock()
  • 写方法要格外小心用错锁类型
  • 业务类和并发控制代码耦合在一起
切面写法
  • 业务方法只需标 @ReadOnly（读）或什么都不标（写）
  • perthis() 关联让每个业务对象拥有自己独立的锁
  • 并发策略集中在一个可复用切面里，随时可替换实现
ch13/workspace/Section13.3.2ReadWriteLockAspectJWay/.../InventoryServiceCachedImpl.java（节选）
@ReadWriteLockManaged
public class InventoryServiceCachedImpl implements InventoryService {

    @ReadOnly
    public boolean isProductAvailable(Product product, int quantity) {
        // 没有一行锁代码——全部由 ReadWriteLockAspect 处理
        return inventory.get(product.getId()).getQuantityOnHand() >= quantity;
    }

    public void removeProduct(Product product, int quantity) {
        inventory.get(product.getId()).deplete(quantity); // 隐式当作“写”操作
    }
}

小结 & 自测

  • 为什么说“Swing 单线程规则”是一个横切关注点？
    因为几乎所有会碰 UI 组件的方法都要遵守它，规则本身和任何单一模块的业务逻辑无关，传统实现必须在调用点“散落”地手动处理，天然符合横切关注点的特征。
  • 第二版方案（按返回值类型判断同步/异步）为什么会出 bug？
    因为“是否需要同步等待”和“返回值是不是 void”并不是一回事——showMessageDialog() 返回 void 但语义上必须阻塞等待用户交互，仅靠返回类型判断会误判。
  • perthis() 在读写锁切面里起什么作用？
    让每个匹配到的目标对象（比如每个 InventoryServiceCachedImpl 实例）都拥有一把独立的 ReadWriteLock，而不是所有对象共用一把全局锁，避免不相关对象之间互相阻塞。
  • 今天用虚拟线程（Java 21+）能替代这一章的线程封闭切面吗？
    不能。虚拟线程解决的是“阻塞式 I/O 太贵”的问题，让你可以开更多轻量线程；但“UI 组件只能在 EDT 上被访问”这类线程封闭规则和线程是否轻量无关，仍然需要显式路由或加锁。
