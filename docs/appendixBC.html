APPENDIX B / C

构建工具：Ant vs. Maven

一句话概括：书里用 Ant 和 Maven 各讲了一遍同样的三件事——织入自己的源码、打包一个切面库、织入别人编译好的 jar。Ant 已经过时，今天直接看 Maven（或 Gradle）部分就够了。

本章你将学到

  • AspectJ 项目里三种最常见的构建任务是什么
  • 为什么 Ant 部分可以跳过，现代项目怎么用 Maven / Gradle 完成同样的事
  • 现代 AspectJ Maven/Gradle 插件该怎么配置

1. 为什么这两个附录要一起看

附录 B 用 Ant、附录 C 用 Maven，做的是完全相同的三件事。 2010 年前后 Ant 和 Maven 在企业里还是并存的两大主流构建工具，所以书里两种都讲了一遍。 但今天几乎不会再有新项目选择 Ant——Maven 和 Gradle 早已是绝对主流。 所以这一页把附录 B 的内容压缩成一句话背景知识，把篇幅留给 Maven / Gradle 的现代写法。

💡 Ant 部分要不要读？

不需要。Ant 版本的 build.xml 用 <iajc> 任务手动指定 aspectjtools.jar 路径、手动拼 classpath，属于“看得懂但没必要再学”的历史写法。 仓库里 appendixBandC/workspace/*/build.xml 保留了原始示例，感兴趣可以翻一翻。

3. 用现代 Maven 做「编译期织入自己的源码」

书中用的是 org.codehaus.mojo:aspectj-maven-plugin，这个插件早已多年未更新。 社区接手维护的现代替代品是 dev.aspectj:aspectj-maven-plugin，配置方式几乎一样，但持续跟进新版 AspectJ 和新版 Java。

pom.xml（编译期织入，Java 17）
<dependencies>
  <dependency>
    <groupId>org.aspectj</groupId>
    <artifactId>aspectjrt</artifactId>
    <version>1.9.22</version>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>dev.aspectj</groupId>
      <artifactId>aspectj-maven-plugin</artifactId>
      <version>1.14</version>
      <configuration>
        <complianceLevel>17</complianceLevel>
        <source>17</source>
        <target>17</target>
      </configuration>
      <executions>
        <execution>
          <goals>
            <goal>compile</goal>
            <goal>test-compile</goal>
          </goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>

用 Gradle 的话，等价写法是 io.freefair.aspectj 插件：

build.gradle（编译期织入）
plugins {
    id 'java'
    id 'io.freefair.aspectj.post-compile-weaving' version '8.10'
}

dependencies {
    aspect 'org.aspectj:aspectjrt:1.9.22'
    implementation 'org.aspectj:aspectjrt:1.9.22'
}

java {
    sourceCompatibility = JavaVersion.VERSION_17
}
⚠️ 版本提醒

AspectJ、dev.aspectj:aspectj-maven-plugin 和 io.freefair.aspectj 的具体版本号请以 Maven Central 和 Gradle Plugin Portal 上的最新版本为准， 不要把本页里的数字当作永远最新的版本。

4. 打包切面库 & 二进制织入，思路不变

书中「打包一个可复用的切面库」和「把切面库织入别人的 jar」这两件事，在现代插件里对应的是同一套配置的两个变体：

  • 切面库：一个只包含 @Aspect 切面、没有具体业务类的普通模块， 正常 mvn install 打成 jar，发布到仓库供别人依赖即可——不需要特殊配置。
  • 二进制织入：在使用方项目的 aspectj-maven-plugin 配置里， 用 <weaveDependencies> 指定要被织入的 jar（对应旧版 -inpath）， 用 <aspectLibraries> 指定切面库（对应旧版 -aspectpath）—— 这部分的配置结构书中和现代版本几乎一致，仓库里 appendixBandC/workspace/SectionB3andC3_2BinaryWeaving/pom.xml 就是一个可以直接参考的例子。
✏️ 动手练习

打开仓库里 appendixBandC/workspace/SectionB1andC1SourceCodeBuildTimeWeaving/pom.xml， 对比它和上面「编译期织入」代码块的差异（主要是 groupId 从 org.codehaus.mojo 换成了 dev.aspectj， source/target 从 1.5 升级到 17）， 试着把这个 pom.xml 改成现代写法，本地跑一次 mvn compile 看能否成功织入。

小结 & 自测

  • 附录 B 和附录 C 讲的是同一件事还是不同的事？
    同一件事——源码级编译期织入、打包切面库、二进制织入这三个任务，只是分别用 Ant（附录 B）和 Maven（附录 C）演示了一遍，因为当时两种构建工具都很主流。
  • 今天还需要学 Ant 部分吗？
    不需要。现代 Java 项目基本都用 Maven 或 Gradle，Ant 属于可以跳过的历史知识，了解“它曾经存在过”即可。
  • 书中的 org.codehaus.mojo:aspectj-maven-plugin 现在还推荐用吗？
    不推荐，该插件已多年缺乏更新。社区维护的现代替代是 dev.aspectj:aspectj-maven-plugin，配置方式高度相似但持续跟进新版 AspectJ 和 Java。
  • "weaveDependencies" 和 "aspectLibraries" 分别对应 ajc 编译器的哪两个旧选项？
    分别对应 -inpath（指定要被织入的已编译代码/jar）和 -aspectpath（指定作为切面库使用的 jar）。
