第 8 章

AspectJ 的织入方式

一句话概括本章：切面写好了，什么时候、用什么方式把它“焊”进程序里？本章讲清楚编译期织入、二进制织入、加载期织入这三条路怎么选。

本章你将学到

  • 织入的两个维度：什么时候织（build-time / load-time）、织什么输入（源码 / 字节码）
  • 编译期源码织入、编译期二进制织入、加载期织入（LTW）三种模式的原理与取舍
  • -javaagent + META-INF/aop.xml 是怎么在 JVM 启动时“劫持”类加载的
  • 现代项目该怎么选：几乎总是编译期织入或 Spring AOP 代理，LTW 只在特殊场景使用

1. 织入的两个分类维度

"织入（weaving）"就是把切面代码和业务代码合并成最终可执行程序的过程。书里从两个维度给织入方式分类：

  • 什么时候织：编译期（build-time，程序还没跑起来就织好了）还是加载期（load-time，程序启动、类被加载的那一刻才织）。
  • 织什么输入：源码（.java/.aj 文件）还是字节码（已经编译好的 .class/.jar，比如第三方库）。

组合起来正好是本章要讲的三种主要模式：

💡 类比

编译期织入像“装修时把水管预埋进墙里”——一次到位，后面用起来最省心，但要动工前就规划好。 加载期织入像“用明装线槽走线”——房子已经装好也能加，随时能改，但多了一层线槽，且改起来要小心别碰坏原有装修（性能/兼容性代价）。

2. 编译期织入：source vs. binary

最常见、最好理解的方式是源码织入：把 ajc 当成 javac 的替代品，直接吃源码吐字节码。 现代项目里，这一步由 Maven/Gradle 插件自动完成，你几乎不会手写 ajc 命令。

如果你没有源码（比如切面来自第三方 jar，或者业务类是第三方库），可以用二进制织入：直接把已编译的 .class/.jar 喂给 ajc，让它在字节码层面完成织入。 本质上，源码织入内部也是"先编译成字节码，再做二进制织入"，只是这一步对你透明。

概念示意：ajc 命令（现代项目里由 Maven 插件自动生成，不需要手敲）
# 源码织入：把切面源码和业务源码一起编译
ajc ajia/banking/*.java ajia/tracing/TraceAspect.aj

# 二进制织入：业务代码已经是 jar，切面代码也是 jar
ajc -inpath services.jar -aspectpath monitoring.jar -outjar woven.jar
⚠️ 容易踩的坑

和 javac 不同，ajc 要求把所有互相关联的源文件一次性传入。 分两次单独编译 ajc ajia/banking/*.java 和 ajc TraceAspect.aj，并不会织入成功——因为 第一条命令根本不知道 TraceAspect 的存在。现代 Maven 插件会自动把整个模块的源码集一起传给编译器，避免了这个问题。

3. 加载期织入（LTW）：JVM 启动时“劫持”类加载

LTW 的核心机制是 JVM 的 Java Agent（书中提到底层用的是 JVMTI，现代 JDK 一直保留了这套机制）。 启动 JVM 时加一个参数：-javaagent:aspectjweaver.jar，AspectJ 的织入器就会挂钩到类加载流程上—— 每当 JVM 要把某个类的字节码正式加载进内存，都会先“路过”织入器，织入器检查这个类是否需要织入切面，需要的话就地修改字节码，再交还给 JVM。

你需要在 classpath 上放一个 META-INF/aop.xml，告诉织入器"要织哪些切面"：

仓库真实文件：ch08/workspace/Section8.4LoadTimeWeaver/src/main/resources/META-INF/aop.xml
<aspectj>
    <aspects>
        <!-- Monitoring 是一个抽象切面，只声明了抽象的 monitored() 切点 -->
        <concrete-aspect name="ajia.monitoring.JDBCMonitoring"
                          extends="ajia.monitoring.Monitoring">
            <pointcut name="monitored" expression="call(* java.sql.*.*(..))" />
        </concrete-aspect>
    </aspects>
</aspectj>

这份 XML 用 <concrete-aspect> 给上一章那个抽象的 Monitoring 切面（monitored() 是抽象切点） 补上了具体定义——"只监控 JDBC 调用"，而且不需要重新编译 Java 代码，改一下 XML、重启应用就能换监控范围。

启动方式（现代命令行等价写法）
# 书中年代（2009）的旧路径写法
java -javaagent:C:\aspectj1.6.5\lib\aspectjweaver.jar -jar app.jar

# 现代等价写法：用 Maven 依赖坐标定位 jar，Java 17/21 上原理完全一样
java -javaagent:$HOME/.m2/repository/org/aspectj/aspectjweaver/1.9.22/aspectjweaver-1.9.22.jar \
     -jar app.jar
⚠️ JPMS（模块系统）与容器化环境的额外注意事项

在 Java 9+ 的模块化世界里，-javaagent 依然管用，但如果织入器需要访问某些模块内部的类， 可能要额外加 --add-opens。在 Spring Boot 可执行 jar（fat jar）里使用 LTW 也需要额外配置类加载器 （-Dspring.application.class-loader 或使用 @EnableLoadTimeWeaving，第 9 章会讲）。 容器/K8s 场景下修改启动命令加 -javaagent 也比较麻烦，这些都是现代项目更倾向于用编译期织入或 Spring AOP 代理、 而不是 LTW 的现实原因。

4. 现代项目该怎么选？

书中年代（2009）的建议
  • 团队用 Eclipse + AJDT → 传统语法 + 编译期织入
  • 探索阶段、临时诊断问题 → LTW，改完就关掉，不留痕迹
  • Java 5 时代 LTW 配置简单，优先考虑 LTW
现代项目推荐
  • Spring / Spring Boot 项目 → 优先用 Spring AOP 代理（ch09），不需要任何织入器
  • 需要 ITD 等原生能力 → Maven/Gradle 插件做编译期织入，IDE 支持已经很成熟（IntelliJ IDEA 内置 AspectJ 支持）
  • 只在“运行中的第三方系统临时挂诊断切面”这种场景才考虑 LTW

✏️ 动手练习

打开仓库 ch08/workspace/Section8.4LoadTimeWeaver/，阅读 run1.sh/run2.sh/run3.sh 三个脚本， 理清它们分别对应"先跑一遍原始应用 → 编译并复制切面 jar → 加上 -javaagent 重启"这三步。 尝试把 aop.xml 里的切点表达式从 call(* java.sql.*.*(..)) 改成同时监控某个业务包，观察输出变化。

小结 & 自测

  • 编译期织入和加载期织入，最终产生的字节码有区别吗？
    没有本质区别——两者产出的“织入后字节码”是一样的，区别只是“在什么时间点付出织入的代价”：编译期在构建时付，加载期在每次类加载时付（带来一定的启动性能开销）。
  • 什么场景下必须用编译期织入，不能拖到加载期？
    涉及类型间声明（ITD）等改变类结构的静态横切时：如果等到加载期才发现某个类多了一个方法，那些在编译期就引用了这个新方法的代码早就编译失败了。
  • LTW 依赖哪个 JVM 参数生效？
    -javaagent:<path>/aspectjweaver.jar，配合 classpath 上的 META-INF/aop.xml 说明要织哪些切面。
  • aop.xml 里的切点表达式有什么限制，是不能用 args() 收集参数吗？
    是的——XML 语法里定义的切点不能收集连接点上下文（不能用 args() 绑定参数），只适合做“范围限定”，具体的通知逻辑还是要写在 Java 切面里。
  • 为什么现代 Spring Boot 项目很少用 LTW？
    因为 Spring AOP 的代理机制（下一章）不需要任何 -javaagent 或字节码织入就能实现绝大多数场景的 AOP 需求，配置更简单、启动更快、和 fat jar/容器化部署的兼容性也更好；只有需要织入非 Spring 管理的对象、或需要 AspectJ 全部能力时才考虑 LTW。
