APPENDIX A

搭建示例工程

一句话概括：全书反复出现的“电商库存系统” Commerce 是什么样子、为什么全书都用它，以及怎么用现代脚手架重新搭一遍。

本章你将学到

  • 贯穿全书的示例项目 Commerce 的业务场景与分层结构
  • 为什么全书 16 章都复用同一个示例，而不是每章换一个新项目
  • 书中 2010 年前后的技术栈（Spring 3 + JPA/Hibernate 3 + Ant/老式 Maven）该怎么对应到今天

1. Commerce 是一个什么样的项目？

Commerce 是一个很小的电商网站：用户可以浏览商品详情、把商品加入购物车、下单； 后端有一个简单的库存管理服务，负责扣减/补充库存。它足够小，能在一章的篇幅里看懂全貌； 但又足够真实——有 Web 层、业务层、持久化层，能装下事务管理、安全、缓存、并发控制等一整套 企业级横切关注点，正好用来演示每一章要讲的 AOP 技术。

这也是作者的一个刻意设计：全书 16 章共用同一个示例代码库（仓库里的 appendixA/workspace/Commerce），而不是每章重开一个新 demo。 好处是你不需要在每一章重新理解一套新业务，注意力可以完全放在“这一章的 AOP 技术怎么应用到我已经熟悉的代码上”。

2. 四层结构一图看懂

图 A-1　Commerce 示例的四层结构：控制器 → 服务层 → 领域对象 → 持久化

关键的领域类只有四个，故意设计得很简单：

  • DomainEntity —— 抽象基类，只放一个 id 字段，避免每个实体类都重复写主键代码；
  • Product —— 商品，有名称、描述、价格；
  • LineItem —— 订单里的一行（某个商品 + 数量）；
  • Order —— 订单，持有多个 LineItem，提供加/删商品、下单、取消等方法；
  • InventoryItem —— 库存记录，提供扣减 deplete() / 补充 replenish() 库存的方法。
💡 贫血模型，先别急着嫌弃

你会发现这些领域类基本只有 getter/setter，没什么“智能”的业务行为——这叫“贫血领域模型”。 作者是故意这么设计的：第 16 章会专门讨论如何用 AspectJ 把行为“注入”回这些领域对象， 让贫血模型重新变“胖”。所以这里的简单不是缺陷，是为后面的章节埋的伏笔。

3. 书中写法 vs. 今天该怎么搭

书写于 2010 年前后，用的是 Spring 3.0 + Spring MVC + JPA 1.0（Hibernate 3.3 实现）+ 需要手动打包成 WAR、部署到独立 Tomcat；构建工具是 Maven 2.2（或 Ant，见附录 B）。 今天做同样的事情，几分钟就能用 Spring Boot 起一个等价的骨架。

书中写法（2010 年前后）
  • Spring 3.0 + Spring MVC，手写多份 XML 配置（application-context.xml / web-context.xml …）
  • JPA 1.0 + Hibernate 3.3，persistence.xml 手动配置方言
  • 打包成 WAR，部署到独立安装的 Tomcat；或用 mvn tomcat:run
  • Log4j 1.x（log4j.xml）
推荐的现代写法
  • Spring Boot 3.x（spring-boot-starter-web），零 XML，自动装配
  • Spring Data JPA + Hibernate 6（内置），或直接用 JdbcClient
  • 内嵌 Tomcat，mvn spring-boot:run 或直接跑 main()
  • SLF4J + Logback（Spring Boot 默认自带）
pom.xml（现代最小骨架，可直接对照书中 Commerce 项目使用）
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.3.4</version>
</parent>

<properties>
  <java.version>17</java.version>
</properties>

<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
  </dependency>
  <dependency>
    <!-- 后面章节要用切面时，加上这一个依赖就够了 -->
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>
  </dependency>
  <dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>runtime</scope>
  </dependency>
</dependencies>

Product、Order、LineItem、 InventoryItem 这几个类里的 JPA 注解（@Entity、 @ManyToOne、@OneToMany ……）在 Jakarta EE 时代 改了包名，从 javax.persistence.* 换成了 jakarta.persistence.*，其余写法基本不用变——这是升级到 Spring Boot 3 时最容易踩的一个坑。

⚠️ 版本提醒

Spring Boot 版本号请以 spring.io 上的最新稳定版为准，这里的 3.3.4 只是示例。

✏️ 动手练习

打开仓库里的 appendixA/workspace/Commerce/src/main/java/ajia/， 对照上面的四层结构图，找出 domain、service、 repository、web 四个包分别对应图里的哪一层； 再试着用上面的 pom.xml 骨架起一个新项目，把 domain 包下的四个类复制过去 （记得把 javax.persistence 换成 jakarta.persistence），感受一下从 XML 配置到 Spring Boot 自动装配的差别。

小结 & 自测

  • 为什么全书 16 章都复用同一个 Commerce 示例，而不是每章换新项目？
    这样读者只需要理解一次业务场景，之后每一章都能把注意力完全放在“这一章的 AOP 技术怎么应用”上，而不用反复学习新的领域模型。
  • Commerce 示例的四层结构分别是什么？
    Web 层（Controller）→ 业务层（Service，事务边界所在）→ 领域对象（Order/Product/LineItem/InventoryItem）→ 持久化层（Repository + JPA/Hibernate）。
  • 什么是“贫血领域模型”？书里为什么故意这么设计？
    指领域类只有数据和 getter/setter，没有承载业务行为。作者故意这样设计，是为第 16 章“用 AspectJ 给领域对象注入行为”做铺垫。
  • 把书中项目升级到 Spring Boot 3 时，最容易踩的一个坑是什么？
    JPA 注解的包名从 javax.persistence.* 变成了 jakarta.persistence.*（Jakarta EE 命名空间迁移），漏改会导致编译或启动失败。
